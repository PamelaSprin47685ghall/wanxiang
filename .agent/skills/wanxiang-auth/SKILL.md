## 决策 52（第一问）：`pwa=true, server=false` 如何运行？

**AI 建议：** PWA 组件拥有独立的最小静态资源 HTTP 服务。因此：
- `pwa=true, server=true`：静态资源服务与 WebSocket 服务可共用同一监听端口和 origin；
- `pwa=true, server=false`：仍启动静态资源 HTTP 服务，但不提供本机 WebSocket 服务；
- PWA 加载后由用户选择或输入远端万象 S 地址；
- `pwa=false`：完全不托管浏览器资源；
- PWA 静态服务不读取 NDJSON、不运行 Agent、不拥有业务投影，只负责 HTML、JS、CSS、manifest 和 service worker。

这样 `pwa-only` 才是真正可运行的模式，而不是单纯导出静态文件。

**已确认（12:33:55）语义：**
- `pwa=true, server=false`：本实例只提供 PWA 客户端，不运行自己的 S；
- PWA 可以连接其他万象 S；
- 为了让浏览器打开 PWA，进程仍需提供最小静态资源服务，但它不提供业务 WebSocket、Agent、NDJSON 或投影；
- `pwa=true, server=true` 时，PWA 默认可以连接同实例 S，也可以切换连接其他 S。

## 决策 52（第二问）：PWA 的永久客户端令牌存在哪里？

此前已经确定"每客户端一个永久令牌"，这意味着 PWA 必须突破最初的"浏览器端完全不持久化"约束。

**AI 建议：** 令牌保存在 IndexedDB，按服务端身份分别存储。记录关系类似：

```text
serverIdentity → serverUrl + clientId + clientToken
```

不建议放在 `localStorage`：IndexedDB 更适合结构化、多服务端凭据；可以按 origin 隔离；后续可加入迁移、吊销和多个连接配置；浏览器环境无法真正防止同源恶意脚本读取，因此不应假装能做到操作系统级密钥保护。

**用户回答（12:35:06）：** "IndexedDB 在 ios 端是本地的吗"

**AI 调研结论（12:35:08）：** 是的。iOS 上的 IndexedDB 数据保存在 **iPhone/iPad 本机的 WebKit 网站数据存储**中，按 origin 隔离；不是存在万象服务器，也不会天然跨设备同步。关闭页面或重启设备后通常仍保留。但它不是 Keychain 式的"不可丢失安全存储"：
- 用户清除网站数据或卸载主屏幕 PWA 后，令牌可能消失；
- 系统存储压力下，默认的 best-effort 数据可能被清理；
- 隐私浏览中的 IndexedDB 只维持到该隐私会话结束；
- 同源 JavaScript 能读取它，因此 XSS 仍可窃取令牌。

主屏幕 PWA 可以调用 `navigator.storage.persist()` 请求持久存储；WebKit 会结合是否为主屏幕 Web App 等条件决定是否批准，但仍不能抵抗用户主动清除数据。

**对万象的建议：** PWA 将长期客户端令牌保存在 IndexedDB；启动后请求 persistent storage。令牌丢失不视为服务端故障，用户重新用 6 位码配对即可。

**已确认（12:36:06）PWA 凭据恢复策略：**
- 每个万象 S 的长期客户端令牌保存在 IndexedDB；
- IndexedDB 被清除、PWA 被卸载或浏览器数据被重置后，令牌丢失属于正常情况；

- PWA 仍不缓存会话或消息，持久化内容仅限连接配置与客户端令牌。

# 28. 令牌提交、吊销与并发连接

## 决策 55：WebSocket 建连时如何提交永久令牌？

浏览器 WebSocket API 不能可靠设置自定义 `Authorization` 请求头；把令牌放在 URL 查询参数中又容易进入代理日志和浏览器记录。

**AI 建议：** 先建立 TLS WebSocket，再把令牌作为第一条协议事件发送。连接在认证前处于受限状态：

```json
{ "type": "auth.present", "token": "<永久令牌>" }
```

服务端在认证完成前：
- 只接受认证和配对相关事件；
- 不发送任何业务状态；
- 不允许 `observe` 或写命令；
- 设置较短认证超时；
- 认证失败后立即关闭连接；
- 不把令牌写入 stderr、NDJSON 或普通诊断日志。

整个过程必须使用 `wss://`；明文 `ws://` 仅允许明确配置的 loopback 本机连接。

**用户回答（12:38:07）：** "嗯"

**已确认（12:38:14）：**
- 永久令牌通过已建立的 `wss://` 连接，以第一条受限认证事件提交；
- 不放入 URL、Cookie 或握手 Header；
- 认证前连接只能处理认证与配对事件；
- 明文 `ws://` 仅可用于明确允许的 loopback 场景。

## 决策 56：配对成功时，先持久化还是先下发令牌？

**AI 建议：** 先将令牌哈希写入 TOML 并重新加载成功，再将令牌原文发送给客户端。顺序如下：

```text
生成高熵永久令牌
→ 将 SHA-256 哈希加入配置
→ 完整重写 TOML
→ 从正式文件重新加载成功
→ 消耗并销毁 6 位配对码
→ 仅向该连接发送一次令牌原文
```

这样客户端收到令牌时，服务端一定已经能够使用它完成后续认证。代价是：若 TOML 已写成功，但发送令牌前连接断开，服务端会留下一个客户端并未取得原文的孤立哈希记录。由于服务端不保存令牌原文，无法补发；用户只能重新配对，之后再吊销孤立记录。相比先发令牌再持久化，这不会产生"客户端以为配对成功，但令牌实际上无法登录"的更危险状态。

**用户回答（12:39:17）：** "嗯"

**已确认（12:39:27）配对提交顺序：**

```text
生成永久令牌
→ 写入令牌哈希到 TOML
→ 从正式文件重新加载成功
→ 销毁配对码
→ 向该连接一次性发送令牌原文
```

客户端收到令牌时，它已经可以用于认证；发送前断线可能留下未被客户端取得的孤立哈希记录。

## 决策 57：孤立令牌记录是否自动清理？

**AI 建议：** 不自动清理。服务端无法可靠区分：客户端完全没收到令牌；客户端收到了令牌，但暂时还没有再次连接；客户端保存成功，但长期离线。因此记录保留在 TOML 中，并通过 `last_seen` 是否为空供管理界面识别。用户可以手动吊销从未成功认证过的记录，避免自动清理误删有效客户端。

**用户回答（12:39:36）：** "嗯"

**已确认（12:39:40）：** 孤立令牌哈希记录不会自动清理，永久保留到用户手动吊销。

## 决策 58：吊销令牌后，现有连接是否立即失效？

**AI 建议：** 立即失效。规则：
- TOML 中删除或标记该令牌哈希为已吊销；
- 配置重新加载成功后，服务端查找所有使用该令牌认证的现有 WebSocket；
- 立即关闭这些连接；
- 后续重连认证失败；
- 不等待连接自然断开；
- 吊销动作不写入 NDJSON，因为认证配置的权威来源是 TOML。

否则被盗令牌即使已吊销，现有长连接仍可能继续观察会话和发送命令。

**已确认（12:40:01）：** 令牌一旦在 TOML 中被吊销并成功重新加载，服务端立即断开该令牌对应的全部现有 WebSocket；后续认证也会失败。

## 决策 59：同一个永久令牌能否建立多个并发连接？

- 每条 WebSocket 独立维护观察集合、全局游标和追赶状态；
- 所有连接共享同一个认证身份；
- 一个连接变慢不影响同令牌下的其他连接；
- 吊销令牌时关闭其全部连接；
- 不限制"一个令牌只能在线一次"，避免新连接误踢掉旧标签页；
- 真正不同的设备应分别配对，以便单独吊销。

## 决策 64：本机桌面 Client 如何首次获得本机 S 的令牌？

**AI 建议：** 自动配对，不走 6 位码。当 `server=true, client=true` 时，同一进程在启动阶段：
1. 为本机桌面 Client 生成高熵永久令牌；
2. 在 TOML 的服务端授权列表中保存其哈希；
3. 在 TOML 的客户端连接配置中保存令牌原文；
4. 完整重写并重新加载 TOML；
5. 桌面 Client 再通过真实 loopback WebSocket 使用该令牌认证。

若已有本机令牌则直接复用。这样仍然完整经过 WebSocket 和认证，只是信任根来自"能启动并写入该实例 TOML 的本机用户"，无需再从同一进程的 `stderr` 抄配对码。

## 决策 65：同源 PWA 是否自动配对？

**AI 建议：** 不自动配对，仍使用 stderr 的 6 位配对码。原因是"由本机 S 托管页面"并不等于"访问页面的人可信"。只要站点可从局域网或公网访问，任何能打开 PWA 的浏览器都属于新客户端。与同进程桌面 Client 不同，服务端无法证明浏览器由启动万象的本机用户控制。因此建议：
- 本机桌面 Client：同进程启动，可自动配对；
- PWA：无论是否同源，首次使用都必须输入 6 位配对码；
- 配对后永久令牌保存到该浏览器的 IndexedDB；
- 后续同源自动连接时直接使用已有令牌；
- IndexedDB 被清除后重新配对。
