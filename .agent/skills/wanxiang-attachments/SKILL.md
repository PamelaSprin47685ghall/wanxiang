# 33. 附件传输与内容寻址

> 覆盖对话决策 71、72。会话时间：2026-08-01 12:57。

## 决策 71：附件如何通过单一 WebSocket 传输？

目前协议只允许 JSON 文本帧，但图片、文档等附件可能很大。考虑到已经确定"一个连接处理一切"，建议：
- 附件仍走同一 WebSocket；
- 使用多个 fire-and-forget JSON 事件分块传输；
- 每个附件拥有 `attachmentId`；
- 二进制内容按固定大小切块后 Base64 编码；
- 顺序发送 `attachment.begin`、多个 `attachment.chunk`、`attachment.complete`；
- 服务端在 `complete` 后校验总长度与 SHA-256，成功后才允许消息引用该附件；
- 未完成上传只保存在临时文件中，不写 NDJSON；
- 连接断开后删除未完成附件，不支持断点续传；
- 完成后的附件作为独立文件永久保存，NDJSON 消息只记录引用和元数据，不把大文件嵌入事件日志。

这样维持了文本 JSON 和单连接约束，同时避免 NDJSON 被 Base64 大对象撑大。

## 决策 72：附件文件如何命名和去重？

**AI 建议：** 使用内容寻址存储，以 SHA-256 作为永久文件标识。例如：

```text
attachments/
  ab/
    cd/
      abcdef...完整哈希
```

消息中的附件引用记录：

```json
{
  "sha256": "abcdef...",
  "size": 123456,
  "mediaType": "image/png",
  "fileName": "photo.png"
}
```

相同内容只保存一份；原始文件名仅作为展示元数据，不参与磁盘路径。这样可以避免路径注入、文件名冲突和重复上传，并能在 `attachment.complete` 时直接判断文件是否已存在。

# 34. 附件清理与删除记账

> 覆盖对话决策 73（两个子决策）。会话时间：2026-08-01 12:58。

## 决策 73（第一问）：无引用附件如何清理？

**AI 建议：** 正常运行时不自动删除；仅由 `doctor --fix` 清理。`doctor --fix` 通过完整 replay 构建当前投影，收集所有仍被消息引用的 SHA-256，然后删除：不被任何有效消息引用的永久附件；超过短暂宽限期的临时上传文件；文件名与实际内容哈希不一致的附件。建议为永久孤儿设置 **24 小时宽限期**，避免"附件已完成保存，但引用消息尚未来得及记账"时被另一个修复进程立即删除。正常运行中的消息删除、会话删除只改变引用关系，不立即碰磁盘文件。

**用户回答（12:58:05）：** "垃圾回收未来有了压缩功能在压缩时处理"

**已确认（12:58:13）：**
- 首版**不执行附件垃圾回收**；
- 未被消息引用、引用后来被删除、或上传完成但最终未记账的内容寻址附件，均可继续留在磁盘；
- 未来引入日志压缩时，由压缩流程根据压缩后的有效状态计算活跃附件集合，并同步清理不可达附件；
- `doctor --fix` 首版不负责附件 GC。

## 决策 73（第二问）：删除消息或会话如何记账？

**AI 建议：** 只追加删除事件，不修改或删除历史 NDJSON。例如删除一条消息：

```json
{
  "type": "message.deleted",
  "version": 1,
  "conversationId": "...",
  "messageId": "..."
}
```

删除会话同理。内存投影和客户端 snapshot 不再展示已删除对象，但旧消息事件仍保留在历史日志中；未来压缩时才真正从新的基线状态中移除。这意味着：
- "删除"是逻辑删除；
- replay 可以确定性恢复删除后的当前状态；
- 不需要跨多个 UTC 文件搜索并改写旧记录；
- 被删除消息引用的附件暂不回收，留待未来压缩处理。

**已确认（12:58:36）：** 删除消息或会话采用追加式 tombstone；历史 NDJSON 永不原地修改，附件清理由未来压缩阶段处理。

# 51. 自动问答 八：附件（Q171–180）

**171. 问：首版单附件默认大小上限是多少？**
答：默认 **64 MiB**，可在 TOML 修改；这是安全资源上限，不改变附件领域语义。置信度：中。

**172. 问：默认上传 chunk 多大？**
答：每块原始数据默认 **256 KiB**，Base64 后放入一个 JSON WebSocket 事件；服务端可以在握手后公布上限。置信度：中。

**173. 问：附件上传完成是否立即成为会话历史？**
答：不会。完成只产生可引用 blob；只有包含该附件引用的消息 commit 后，它才进入会话历史。

**174. 问：上传内容与已有 SHA-256 相同时怎么办？**
答：复用已有 blob，不重复写文件；仍可保留本次消息提供的原始文件名和媒体类型元数据。

**175. 问：客户端提供的文件名是否直接用于路径？**
答：绝不用于存储路径。它只是经过长度和字符清理后的展示元数据。

**176. 问：媒体类型相信客户端吗？**
答：作为声明值保存，同时可做轻量嗅探；冲突时保留两者，不因嗅探结果改写原始声明。

**177. 问：附件下载走 HTTP 还是 WebSocket？**
答：首版走同一业务 WebSocket，以 begin/chunk/complete 事件传输，不增加新的业务 HTTP API。

**178. 问：附件下载支持 Range 或断点续传吗？**
答：首版不支持；中断后重新请求完整附件。

**179. 问：历史引用的 blob 丢失怎么办？**
答：历史引用保留，查询中标记附件缺失，doctor 报告；不删除消息，也不伪造替代文件。

**180. 问：已完成但尚未被消息引用的附件何时删除？**
答：首版不自动删除，与"不做附件 GC"保持一致；未来压缩按可达性统一处理。
