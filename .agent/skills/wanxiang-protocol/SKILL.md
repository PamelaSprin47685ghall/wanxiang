# 14. 传输协议：muxed WebSocket、fire-and-forget

> 覆盖对话决策 25（三个子决策）。会话时间：2026-08-01 11:48–11:51。

## 决策 25（第一问）：PWA 与 Linux S 使用什么通信方式？

**AI 建议：** 首版采用普通 HTTP 命令接口 + SSE 事件流，不使用 WebSocket。建议职责：

```text
HTTP POST
- 发送或排队消息
- 取消生成
- Tool 审批
- 修改配置
- 其他写命令

HTTP GET
- 会话列表
- 历史消息
- 当前运行状态

SSE
- queued / committed
- 流式模型增量
- 完整消息提交通知
- Tool Call / Tool Result 通知
- 生成结束、失败或取消
```

理由：SSE 天然适合服务器到 PWA 的流式输出；写操作继续使用独立 HTTP 请求，幂等和错误码更清晰；浏览器自动重连、反向代理和调试都比 WebSocket 简单；不需要维持一套双向帧协议；Linux C 调用其他 Linux S 时也能复用同一套协议；Agent Framework 本身已有基于 Responses/SSE 的 hosting 路径，可借鉴其传输方式，但应用仍保留自己的排队与 CQRS 边界。

**用户回答（11:48:23）：** "考虑到未来支持服务器端推送，直接用 muxed websocket (一个连接处理一切)"

**已确认（11:48:28）首版通信方式：**
- PWA 与 Linux S 之间使用**单条复用 WebSocket 连接**；
- 查询、命令、流式输出、状态通知、服务端主动推送都走同一连接；
- 不再区分 HTTP 命令通道与 SSE 推送通道；
- Linux C 调用远端 Linux S 时也应复用同一协议模型；
- 连接只是传输层，NDJSON/CQRS、`queued → committed`、消息级记账等语义保持不变。

## 决策 25（第二问）：复用协议采用请求 ID，还是逻辑子流 ID？

**AI 建议：** 同时保留 `requestId` 和 `streamId`，但职责严格分开：

```json
{
  "type": "command",
  "requestId": "019c...",
  "streamId": "conversation:019b...",
  "payload": {}
}
```

- `requestId`：标识一次请求及其直接响应，用于错误、确认和超时匹配；
- `streamId`：标识一个长生命周期逻辑通道，例如某个会话、生成过程或服务器通知流；
- 同一个 `streamId` 上可以连续出现 `queued`、`committed`、流式 delta、完整消息、tool 消息、完成或失败；
- 多个会话可在一条 WebSocket 上并发交错传输；
- 每个帧还应有 `type`，不要依赖字段组合猜测帧种类。

只使用 `requestId` 会让长时间生成和服务端主动推送很别扭；只使用 `streamId` 又不利于精确回应单次命令。

**用户回答（11:50:42）：** "这两个都不用，尝试全部设计成 fire-forget 协议"

**已确认（11:50:55）：** muxed WebSocket 不使用 `requestId` 或 `streamId`，整体按 **fire-and-forget 事件协议**设计。所有帧都是独立事件，不存在"请求/响应"概念；关联完全依赖已有业务标识：

```json
{
  "type": "chat.user-message.enqueue",
  "conversationId": "019c...",
  "invocationId": "019c...",
  "commandId": "sha256:...",
  "payload": {}
}
```

服务器之后可异步发送：

```json
{ "type": "chat.user-message.queued", "conversationId": "019c...", "invocationId": "019c..." }
```

```json
{ "type": "chat.user-message.committed", "conversationId": "019c...", "invocationId": "019c...", "id": 1843 }
```

流式 delta、完整消息、Tool Call、Tool Result、错误、服务器主动通知也都是同级事件。客户端不等待某个 transport response；它只根据 `type` 和领域 ID 更新本地状态。这样仍能在单连接中交错处理多个会话，同时避免重新引入隐性的 RPC 模型。

## 决策 25（第三问）：是否采用完全对称的事件协议？

**AI 建议：是。** C→S 与 S→C 使用同一个事件外壳和事件分发机制，不区分 command frame、response frame、notification frame；区别仅由 `type` 的命名和处理权限决定。

**用户回答（11:51:21）：** "是的"

**已确认（11:51:29）：** WebSocket 两端采用**完全对称的 fire-and-forget 事件协议**。
- 不存在请求、响应、通知三类传输概念；
- 所有消息都是独立事件；
- C→S 与 S→C 使用同一事件外壳和同一分发机制；
- 状态关联只依赖 `conversationId`、`invocationId`、`commandId` 及其他领域标识；
- 哪些事件允许由哪一端发送，由权限和事件类型规则决定；
- 一条连接可交错承载多个会话、流式增量和服务器主动推送。

# 15. 断线重连与同步

## 决策 26：WebSocket 断线后是否补发服务器事件？

**AI 建议：** 首版不提供传输层补发。WebSocket 只负责在线实时投递：
- 流式 delta 丢失后不补发；
- `queued` 属于临时状态，不补发；
- 已经写入 NDJSON 的完整消息和 `committed` 状态，可以在重连后通过一次"同步当前状态"事件重新获得；
- 服务端不保存每条连接的发送游标，也不维护 transport event 日志；
- 重连后的客户端应主动声明自己当前关注的会话，服务器随后推送这些会话的当前权威状态。

也就是说，**补偿依靠 CQRS 查询投影，而不是重放 WebSocket 帧**。否则实际上还要设计第二套带序号、确认、保留期限和重放游标的事件日志。

**用户回答（11:51:55）：** "同意"

**已确认（11:52:04）：**
- WebSocket 帧不做逐帧补发；
- 流式 delta 与临时 `queued` 状态断线即丢失；
- 服务端不维护连接级游标或传输事件日志；
- 重连后通过 CQRS 内存投影重新同步当前权威状态；
- NDJSON 仍是唯一永久事实来源。

## 决策 27：重连同步采用全量还是按需？

**AI 建议：** 首版采用按需同步，不在连接建立后推送全部会话和全部消息。客户端重连后发送独立事件，声明当前需要的视图：

```json
{ "type": "conversation.observe", "conversationId": "..." }
```

服务端随后推送：

```json
{
  "type": "conversation.snapshot",
  "conversationId": "...",
  "payload": {
    "messages": [],
    "runtimeState": "idle"
  }
}
```

会话列表单独通过：

```json
{ "type": "conversation-list.observe" }
```

同步原则：
- snapshot 是当前投影，不是 WebSocket 历史重放；
- 当前打开的会话同步完整消息；
- 会话列表只同步摘要，不携带全部消息；
- 客户端切换会话时再观察目标会话；
- 服务端可在被观察的会话发生变化时主动推送新 snapshot 或增量事件；
- PWA 不保存持久缓存，因此不需要"从客户端已有版本继续同步"的复杂协议。

**用户回答（11:52:30）：** "同意"

**已确认（11:52:36）：**
- PWA 通过显式 `observe` 事件按需订阅视图；
- 会话列表只同步摘要；
- 当前打开的会话同步完整消息与运行状态；
- snapshot 是当前 CQRS 投影，不是 WebSocket 历史重放；
- PWA 不保存持久缓存，因此不需要增量游标或客户端版本协商。

# 16. 观察（Observe）模型

## 决策 28：观察关系是否绑定 WebSocket 连接？

**AI 建议：** 绑定当前连接，并在断线时自动全部释放。语义如下：
- `conversation.observe` 将会话加入该连接的观察集合；
- `conversation.unobserve` 主动取消；

- 不按用户或设备跨连接保存订阅；
- 同一连接重复 `observe` 应幂等，只重新推送一次最新 snapshot；
- 一个会话可以同时被多个连接观察，提交后向所有观察者推送。

观察关系属于临时传输状态，不属于业务事实；跨连接保存会引入无效订阅、离线消息积压和设备状态管理。

## 决策 29：观察期间推送全量快照还是增量更新？

**AI 建议：** 首次 `observe` 推送完整 snapshot，之后只推送增量事件。每个权威增量都携带对应的全局日志 `id`：

```json
{
  "type": "conversation.message-committed",
  "conversationId": "...",
  "id": 1843,
  "payload": {
    "...": "Agent Framework message JSON"
  }
}
```

建议规则：
- 首次观察：推送完整会话 snapshot，并附带当前最新 `id`；
- 持续观察：只推送新提交的完整消息、删除、重命名等增量；
- 流式 delta 没有日志 `id`，属于临时展示；
- 客户端若发现权威事件 `id` 与预期不符，不尝试补帧，重新发送 `observe` 获取完整 snapshot；
- 不在每次变化后重复推送整个会话，避免长对话产生大量重复数据。

**已确认（11:53:38）：**
- 首次 `observe` 返回完整 snapshot；
- 后续只推送权威增量；
- 流式 delta 属于临时状态，不带永久日志 `id`；
- 客户端检测到状态不连续时，不补帧，重新 `observe` 获取完整 snapshot。

## 决策 30：如何判断会话增量是否连续？

这里不能直接要求全局日志 `id` 连续。全局 `id` 可能是：

```text
1843：会话 A 消息
1844：配置修改
1845：会话 B 消息
1846：会话 A 消息
```

观察会话 A 的客户端正常只会收到 `1843` 和 `1846`，中间的空洞并不代表丢帧。

**AI 建议：** 为每个会话投影维护连续递增的 `revision`：

```json
{
  "type": "conversation.snapshot",
  "conversationId": "...",
  "revision": 27,
  "lastCommitId": 1843,
  "payload": {}
}
```

```json
{
  "type": "conversation.message-committed",
  "conversationId": "...",
  "previousRevision": 27,
  "revision": 28,
  "commitId": 1846,
  "payload": {}
}
```

语义：`commitId` 对应 NDJSON 的全局 `id`，用于定位永久事实；`revision` 只表示该会话投影的变化次数；客户端当前是 `27`，只接受 `previousRevision = 27` 的增量；不匹配时丢弃该增量并重新 `observe`；`revision` 可由 replay 自然重建，不必成为独立事件字段；流式临时事件不推进 `revision`。

**用户回答（11:54:42）：** "乐观相信会话增量连续，除非被其他业务逻辑顺便证明错误，否则就相信它就行了。"

**已确认（11:54:52）：**
- 不引入会话级 `revision`；
- 不主动检测增量是否缺失或乱序；
- 客户端乐观相信当前 WebSocket 上收到的增量连续、有效；
- 只有其他业务逻辑明确发现状态矛盾时，才重新 `observe` 获取完整 snapshot；
- 已持久化事件仍可携带全局 NDJSON `id`，但客户端不据此进行连续性校验。

# 17. 发送顺序、游标与慢客户端

> 覆盖对话决策 31、32（两个子决策）、33、34。会话时间：2026-08-01 11:55–12:00。

## 决策 31：同一连接上的发送顺序如何保证？

**AI 建议：** 每条 WebSocket 连接只允许一个逻辑发送者，通过单一 FIFO 发送队列写 socket。生成 delta、消息提交、Tool 结果和主动推送等生产者都只能向队列投递，不得并发直接调用 WebSocket send。这样利用 WebSocket 自身的有序传输，保证服务器决定的事件顺序与客户端接收顺序一致，也不需要额外序号。

**用户回答（11:55:13）：** "同意"

**已确认（11:55:18）：** 每条 WebSocket 连接采用**单写者 FIFO 发送队列**，所有事件生产者只向队列投递，禁止并发直接写 socket。连接内顺序由服务器单点确定，不再额外引入传输序号。

## 决策 32（第一问）：慢客户端如何处理发送队列积压？

**AI 建议：** 发送队列设硬上限，超过后直接断开该 WebSocket。建议规则：
- 每连接队列按"帧数 + 总字节数"双重限制；
- 流式 delta 不做无限缓存；
- 队列达到上限后，服务端关闭连接；
- 不丢弃中间事件后继续发送，因为那会让客户端处于不可判断的不完整状态；
- 客户端重连后重新 `observe`，恢复权威 snapshot；
- 已排队但未提交的用户消息仍可能丢失，这与此前约定一致；
- NDJSON 写入和 Agent 执行不因某个慢客户端被阻塞。

**用户回答（11:57:24）：** "容忍任何慢客户端，但代价最多是个游标。同时可以多客户端连接同一个对话，各自一个游标即可。慢不怕，他慢他的，在追上最新之前，他只读。"

**已确认（11:57:42）慢客户端策略：**
- 不因发送慢而断开；
- 服务端不为客户端维护无限发送队列，只维护一个读取游标；
- 多个客户端可以同时观察同一 `conversationId`，各自拥有独立游标；
- 落后的客户端继续追赶已提交事件；
- 在追上当前最新状态前，该客户端只能读取，不能发送会改变状态的事件；
- 一个客户端变慢不会阻塞 Agent、NDJSON 写入或其他客户端；
- 这意味着权威增量必须能从内存投影或 NDJSON 提交流重新读取，而不能只是一次性 WebSocket 帧。

## 决策 32（第二问）：游标使用全局提交 `id`

**AI 建议：** 每个观察者使用一个全局 NDJSON 提交 `id` 作为游标，不再创建会话级序号。服务端从 `cursor + 1` 向后读取全局提交，过滤出该连接所观察会话相关的事件；无关提交直接跳过。追到当前全局最新 `id` 后，客户端恢复可写。优点是：NDJSON 已经天然提供严格连续的全局 `id`；不需要维护第二套会话序号；服务端只保存每个观察者的一个整数；UTC 日志分文件也不影响游标语义；多会话观察可以共用同一个全局游标。

**用户回答（11:57:59）：** "可以"

**已确认（11:58:09）：**
- 每个连接使用全局 NDJSON 提交 `id` 作为追赶游标；
- 服务端从游标之后扫描全局提交流，并过滤出该连接观察范围内的事件；
- 多个客户端观察同一会话时各自维护独立游标；
- 客户端尚未追到当前最新全局 `id` 时，只读；
- 追赶不会阻塞业务执行或其他客户端。

## 决策 33：游标代表"已发送"还是"客户端已应用"？

**AI 建议：** 游标代表客户端已经成功应用到本地界面的最后一个全局提交 `id`。客户端处理完一批权威事件后，发送独立事件：

```json
{ "type": "cursor.advanced", "id": 1846 }
```

服务器据此更新该连接的游标。只有满足：

```text
客户端游标 == 服务端当前最新提交 id
```

该连接才恢复写权限。

不建议以"服务器已经写入 WebSocket"作为游标，因为事件进入 socket 缓冲区不代表 PWA 已经解析并应用；慢客户端可能被过早视为已追平。`cursor.advanced` 仍是 fire-and-forget 事件，不构成请求-响应协议。首次收到 snapshot 后，客户端应用完整 snapshot，再把游标推进到 snapshot 携带的 `lastCommitId`。

**用户回答（11:58:42）：** "可以"

**已确认（11:58:53）：**
- 游标表示客户端**已经成功应用**的最后一个全局提交 `id`；
- 客户端通过独立的 `cursor.advanced` 事件推进游标；
- snapshot 应用完成后，客户端推进到其 `lastCommitId`；
- 只有客户端游标追到服务器当前最新提交 `id`，该连接才获得写权限。

## 决策 34：慢客户端的追赶流量如何限速？

**AI 建议：** 采用确认驱动的分批推送。服务端每次最多推送一个有限批次，例如不超过 256 KiB；随后暂停该连接的权威增量发送，直到客户端发送 `cursor.advanced`，再从新游标继续读取下一批。实时流式 delta 在客户端未追平时不发送，因为它不是可重放的权威状态；客户端追平后才重新接收实时流。这样任意慢客户端只占用连接状态和游标，不会形成无限内存队列，也不会拖慢其他客户端或服务端业务。

**用户回答（12:00:27）：** "可以"

**已确认（12:00:42）追赶机制：**
- 每批权威事件设大小上限；
- 服务端发送一批后暂停；
- 客户端应用完成并发送 `cursor.advanced` 后，再发送下一批；
- 未追平时不接收不可重放的实时流式 delta；
- 每个慢客户端只消耗连接状态、游标和有限批次缓冲。

# 18. 写权限、陈旧检测与重试

> 覆盖对话决策 35、36、37、38。会话时间：2026-08-01 12:01–12:04。

## 决策 35：写权限应比较全局最新 `id`，还是观察范围水位？

目前"客户端游标必须等于服务器全局最新 `id` 才能写"存在一个问题：客户端只观察会话 A，但会话 B、配置、统计等无关业务持续产生新提交时，它可能永远追不上不断前移的全局尾部，即使会话 A 的状态完全是最新的。

**AI 建议：** 游标仍使用全局提交 `id`，但写权限只比较该连接当前观察和操作范围的 `relevantWatermark`。服务端扫描全局日志时可以跳过无关提交，但仍将游标推进越过它们。写入某个会话时，只要求：

```text
客户端已应用该会话最后一条相关提交
```

而不是要求它理解整个服务器的所有业务状态。对于跨领域命令，则检查该命令涉及的所有投影水位。例如修改全局 Provider 配置，就必须先同步 Provider 配置投影。

**用户回答（12:01:23）：** "当然按命令涉及的投影是否追平判断"

**已确认（12:01:33）：** 写权限按**该命令实际涉及的投影是否追平**判断，而不是要求客户端追平整个服务器的全局尾部。例如：
- 向会话 A 发送消息：只检查会话 A 及其必要配置投影；
- 修改 Provider 配置：检查 Provider 配置投影；
- 跨会话操作：检查所有受影响投影；
- 无关会话产生的新提交，不影响当前命令的写权限。

## 决策 36：落后客户端发出的写命令如何处理？

# 32. WebSocket 帧格式与版本协商

## 决策 68：WebSocket 帧采用文本 JSON 还是二进制格式？

**AI 建议：** 首版只使用 UTF-8 JSON 文本帧。规则建议为：
- 每个实时协议事件占一个 WebSocket message；
- 不依赖换行分隔，也不把多个事件拼接进一个文本帧；
- 追赶历史时允许一个事件携带 `items` 数组，作为有限批次；
- Agent 消息 payload 直接嵌入 JSON，不二次转义为字符串；
- 首版不支持 MessagePack、CBOR、Protobuf 或自定义二进制编码；
- 收到二进制帧即视为协议错误并关闭连接；
- 未来若数据量证明 JSON 成为瓶颈，再通过明确的协议版本协商增加二进制编码。

这样最符合"透明映射"、易调试以及 `stderr` 忠实诊断的目标，也避免首版同时维护两套序列化格式。

## 决策 70（第一问）：未知事件能否一律忽略？

**AI 建议：** 不能一律忽略；事件外壳增加 `required`：

```json
{
  "type": "conversation.message-committed",
  "required": true,
  "payload": {}
}
```

处理规则：
- 已知事件：正常处理；
- 未知且 `required=false`：忽略，连接继续；
- 未知且 `required=true`：立即关闭连接，要求升级客户端或服务端；
- 所有会改变权威状态、认证状态、游标或写权限的事件必须为 `required=true`；
- 纯提示、可选 UI 元数据、未来增强信息可为 `required=false`；
- 默认值应为 `true`，避免发送方忘记标记时被接收方静默忽略。

否则旧客户端若忽略新的关键事件，可能仍以为自己已经追平并获得错误写权限。

**已确认（12:48:04）协议版本策略：**
- `protocol.hello` 只携带一个整数版本号，例如 `version: 1`；
- 客户端与服务端版本必须**完全相等**；
- 不划分 major/minor；
- 不引入 `required` 字段；
- 不支持同版本内"忽略未知事件"的兼容策略；
- 版本一致却收到未知事件，视为实现错误或协议违规，记录到 `stderr` 并关闭连接。

# 47. 自动问答 四：Observe、快照与慢客户端（Q131–140）

**131. 问：重复 observe 同一 scope 怎么处理？**
答：幂等处理，替换该连接上相同 scope 的观察状态并重新发送当前快照。

**132. 问：客户端是否需要显式 unobserve？**
答：支持显式 unobserve，以便释放服务端状态；断线时也自动释放全部 observe。

**133. 问：同一连接能否观察多个会话？**
答：可以，每个会话是独立 scope，但共享该连接的全局 applied cursor。

**134. 问：大型快照是否放在一个巨大 WebSocket 消息中？**
答：不放。使用 `snapshot.begin`、若干 snapshot item、`snapshot.end`，全部以 scope 和 `lastCommitId` 关联。

**135. 问：客户端何时为快照发送 `cursor.advanced`？**
答：只有完整应用 `snapshot.end` 后，才能推进到该快照的 `lastCommitId`。

**136. 问：快照中途断线怎么办？**
答：丢弃未完成快照；重连后重新 observe，不做快照续传。

**137. 问：服务端发送队列是否无限增长？**
答：不能。每条连接只保留有限在途批次；一旦落后，就停止堆积权威增量，转为从 cursor 分批 catch-up。

**138. 问：落后期间的流式 delta 怎么办？**
答：直接丢弃。客户端追平后只恢复新的实时 delta，不补发旧 delta。

**139. 问：客户端长时间不推进 cursor 是否断开？**
答：不因"慢"而自动断开；只要连接活着且协议正常，服务端维持受限状态，不无限占用内存。

**140. 问：是否增加业务层 heartbeat 事件？**
答：不增加。使用 WebSocket/服务器基础设施的 ping、pong 和空闲检测，不污染业务协议。

# 48. 自动问答 五：命令、幂等与错误（Q141–150）

**141. 问：fire-and-forget 下客户端如何知道命令成功？**

答：发送独立 `command.rejected`，包含稳定错误代码、面向用户的信息和可选诊断信息，不暴露密钥。

**144. 问：重复收到已提交的同一 `commandId` 怎么办？**
答：不再次执行，重新发送原提交结果，视为幂等成功。

**145. 问：同一 `commandId` 对应不同规范 payload 怎么办？**
答：视为严重实现或哈希冲突错误，写 stderr 并拒绝；绝不把它当作正常重复。

**146. 问：canonical JSON 如何处理对象字段？**
答：字段按稳定字典序排列；字符串和数字使用固定编码；数组保持业务顺序；忽略纯传输字段。

**147. 问：命令 schema 是否独立版本化？**
答：命令类型包含协议内固定语义；不在同一协议版本中悄悄改变。破坏性修改提升整体 protocol version。
