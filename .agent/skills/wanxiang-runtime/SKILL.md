# 24. 运行模式：单进程与三开关

> 覆盖对话决策 49、50（两个子决策）。会话时间：2026-08-01 12:29–12:31。

## 决策 49：Linux UI 与服务端采用同进程还是独立进程？

**AI 建议：** 首版采用一个进程、一个可执行文件，同时承载 Linux UI 与服务端。进程内部仍保持严格边界：

```text
Linux UI Client
      │
      │ loopback muxed WebSocket
      ▼
Linux Server
      │
      ├─ Agent runtime
      ├─ NDJSON 单写者
      ├─ 内存投影
      └─ TOML 配置
```

这意味着：
- 启动一个 `wanxiang` 进程即可得到本地 C+S；
- UI 与服务端不得直接调用彼此业务对象；
- 即使同进程，也必须经过真实 WebSocket 编解码、认证和事件分发；
- 关闭 Linux UI 即结束整个实例及其服务端；
- 需要纯服务端运行时，使用同一可执行文件的 `--headless` 模式，不启动窗口；
- 多开 `wanxiang` 时，每个进程使用独立配置目录、日志目录和监听端口，彼此完全无关。

相比拆成两个操作系统进程，这更符合已经确定的"每个实例严格单进程"，也减少首版的进程监管、升级协调和本地发现复杂度。

**用户回答（12:29:58）：** "同意首版每个 Linux 实例只有一个 wanxiang 进程，UI 与 S 同进程但只能通过 loopback WebSocket 交互，并支持同进程的 --headless 模式"

**已确认（12:30:09）首版 Linux 运行拓扑：**
- 每个实例只有一个 `wanxiang` 进程；
- 默认模式同时运行桌面 UI 与服务端；
- `--headless` 只运行服务端；
- 本地 UI 也必须通过真实 loopback WebSocket、认证和协议编解码访问服务端；
- 多开进程彼此完全独立。

## 决策 50（第一问）：PWA 是否由同一个服务端托管？

**AI 建议：是。** Linux S 同时提供 PWA 静态资源和 muxed WebSocket 端点，默认使用同一个 origin：

```text
https://host/
https://host/ws
```

这样可以：一个进程、一个端口完成部署；避免 CORS 与跨域 WebSocket 配置；PWA 天然连接提供它的那个实例；PWA 版本与服务端协议版本一起发布；反向代理只需转发一个站点。桌面 UI 的资源仍打包进 Linux 可执行程序；PWA 是同一客户端代码的浏览器构建产物，由服务端内嵌或从安装目录读取。

**用户回答（12:31:04）：** "可以。另外 linux 有 pwa only 和 client only 模式，说白了是 server client pwa 三个布尔八种组合"

**已确认（12:31:15）Linux 单一可执行文件由三个独立布尔开关组成：**
- `server`：运行万象服务端、Agent 执行、NDJSON、内存投影和 WebSocket 端点；
- `client`：运行 Linux 桌面客户端；
- `pwa`：托管 PWA 静态资源。

因此存在八种组合，包括完整 `server + client + pwa`、`pwa-only`、`client-only`、`server-only` 等。客户端与服务端仍通过 WebSocket 隔离。

> 注：决策 51 随后加入第四个开关 `fix`，运行模式扩展为 16 种组合，以实现版为准。

## 决策 50（第二问）：三个开关全为 `false` 时做什么？

**AI 建议：** 允许该组合，但只执行配置加载和校验，随后以成功状态退出：

```text
server = false
client = false
pwa = false
```

它不进入常驻状态，也不监听端口。这样八种组合在语法上都有效，同时该模式可用于部署前检查 TOML 是否可读取、解析和通过约束校验。

**用户回答（12:31:41）：** "三个开关全为 false 时就是一般意义上的 doctor 模式"

**已确认（12:31:56）：** `server=false, client=false, pwa=false` 为标准 **doctor 模式**，而不只是 TOML 语法检查。它应检查配置、目录权限、NDJSON 连续性与可 replay 性、端口可用性、运行依赖及静态资源完整性，然后输出诊断结果并退出。

# 25. doctor 与 --fix

> 覆盖对话决策 51（两个子决策）。会话时间：2026-08-01 12:32–12:33。

## 决策 51（第一问）：doctor 是否允许修复数据？

**AI 建议：** doctor 默认严格只读。即使发现 NDJSON 尾部损坏，也只向 `stderr` 报告损坏文件、字节偏移、预期 `id` 和异常，不执行正常启动时的静默截尾。否则用户只是运行诊断，就可能永久改变现场。正常 `server` 启动仍按既定规则自动截尾；未来可另设显式 `--doctor-fix`，但不属于首版默认行为。

**用户回答（12:32:39）：** "另设 --fix ，因此共 16 模式"

**已确认（12:32:44）运行模式由四个布尔量构成：**
- `server`
- `client`
- `pwa`
- `fix`

共 **16 种组合**。其中：
- `0000`：只读 doctor；
- `0001`：doctor + 自动修复；
- 其余组合启动所选运行组件；
- `fix` 决定启动检查发现问题时是否允许修复。

## 决策 51（第二问）：`--fix` 在非 doctor 模式中的执行顺序

**AI 建议：** 先执行完整 doctor/fix，再决定是否启动组件：

```text
加载并检查
→ fix=false：发现阻断性问题则退出
→ fix=true：执行可用修复并重新检查
→ 检查通过后启动 server/client/pwa
```

也就是说，`server=true, fix=true` 不是运行期间持续修复，而是**启动前修复一次，然后正常运行**。运行期间仍按既定的自动截尾、stderr 和 best-effort 规则处理。这样 16 种模式的语义统一，也避免 `--fix` 在服务运行期间不断修改现场。

**用户回答（12:32:57）：** "对的"

**已确认（12:33:05）：** `--fix` 只作用于**启动前的 doctor 修复阶段**。完成修复并重新检查通过后，才启动所选择的组件；运行期间不会常驻执行 doctor 修复。

# 44. 自动问答 一：进程、启动与关闭（Q101–110）

> 第 101–200 项自动问答的一部分。答案以已确认的 100 项决策为主要依据；上传文件仅提供 F#、Avalonia、Agent Framework 与 C/S 架构的初始背景，后续 clean-room、NDJSON、WebSocket 等决定以对话为准。

**101. 问：收到 SIGTERM 后是否立即退出？**
答：不立即退出。停止接受新命令和新生成，取消运行时工作，排空单写者并 flush，随后退出。

**102. 问：优雅关闭是否设置内部固定超时？**
答：首版不设置全局固定超时。第一次终止信号进入优雅关闭，第二次终止信号立即退出；外部服务管理器可设置最终 kill 超时。

**103. 问：commit 已 flush，但投影更新前进程崩溃怎么办？**
答：commit 已经是事实。重启时从 NDJSON replay，重新得到投影，不回滚该 commit。

**104. 问：投影更新成功，但权威增量尚未发送时崩溃怎么办？**
答：客户端重连并重新 observe，从权威投影恢复；不需要重放旧 WebSocket 帧。

**105. 问：同一数据目录能否同时被两个 S 进程打开？**
答：不能。S 启动时获取数据目录独占锁；获取失败则启动失败，不尝试多写者协调。

**106. 问：两个完全独立的 S 如何共存？**
答：使用不同数据目录、不同 TOML、不同 `instanceId` 和不同监听地址，它们之间没有隐式关系。

**107. 问：客户端模式是否需要数据目录独占锁？**
答：不需要。纯客户端只读取自己的连接配置；只有启用 S、可能写永久业务状态的进程需要服务端数据锁。

**108. 问：系统时区变化是否影响日志分片？**
答：不影响。日志文件日期、commit 时间和所有永久时间均使用 UTC；本地时区只用于 UI 展示。

**109. 问：系统时钟向后跳时是否重新写入较早日期文件？**
答：不重新打开更早日期文件。当前日志日期不得小于最后持久化日志日期，避免更高 ID 出现在文件序列前部。

**110. 问：启动组件的顺序是什么？**
答：解析 CLI 和 TOML → 获取目录锁 → doctor/fix → replay → 建立投影 → 初始化配置注册表 → 启动监听器 → 启动客户端 UI。任何客户端连接都不能早于服务端就绪。
