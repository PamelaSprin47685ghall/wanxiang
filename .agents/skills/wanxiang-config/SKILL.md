# 20. 配置持久化与密钥管理

## 决策 41（第一问）：`stderr` 是否允许包含完整敏感 payload？

**AI 建议：** 允许完整输出，不做脱敏。理由是自动脱敏可能再次丢掉定位问题所需的字段，也可能因 schema 透明而无法可靠识别敏感信息。代价是必须明确：stderr 仅写本机受限目标；文件权限至少为当前用户独占；不默认上传到第三方日志平台；文档中标明 stderr 可能包含对话、Tool 参数、API 返回及密钥。

**用户回答（12:11:41）：** "stderr 内容完整，密钥不存，因为密钥对调试无用。"

**已确认（12:11:48）：**
- `stderr` 忠实输出被截掉的完整原始提交、异常类型、消息、堆栈、文件位置和字节偏移；
- **密钥本身不进入 NDJSON，因此也不会出现在 `rawCommit` 中**；
- 日志不做面向业务内容的脱敏，但认证凭据属于结构上禁止持久化的数据，而不是事后打码的数据；
- 若异常对象或第三方库错误消息意外携带密钥，应在写 `stderr` 前只针对已知凭据值做精确替换，不删减其他上下文。

## 决策 41（第二问）：密钥永久保存在哪里？

**AI 建议：** 首版使用独立的本机 secret store，不进入事件日志，也不进入普通内存投影。Linux x64 可采用：首选系统 secret service（Secret Service / libsecret）；系统不可用时，退化为权限 `0600` 的独立加密文件；NDJSON 只保存稳定的 `credentialRef`；Agent 调用前按 `credentialRef` 临时取出密钥；PWA 永远不能读取已有密钥明文，只能提交"设置、替换、删除"动作；查询配置时只返回 `configured: true/false` 或掩码提示。

**已确认（12:15:08）配置模型：**

## 决策 41（第三问）：TOML 更新失败时采用什么语义？

**AI 建议：** TOML 是配置的唯一权威来源，但运行时保留"最后一次有效配置"。具体规则：
- 每次检测到文件变化，都读取并完整解析整个 TOML；
- 只有语法、类型和必要约束全部通过，才一次性替换内存配置；
- 若文件不存在、读取失败或内容非法：向 `stderr` 忠实打印异常；继续使用最后一次有效配置；不部分应用可解析字段；不自动覆盖或修复用户编辑的文件；
- 应用写配置时采用"临时文件 → `flush` → 同目录原子重命名"，避免 watcher 读到半写文件；
- 配置变化不写入 NDJSON，因为 TOML 本身就是配置事实来源。

**已确认（12:15:56）TOML 运行语义：**
- TOML 是全部配置的唯一权威来源；

## 决策 42（第一问）：应用修改 TOML 时是否保留注释与未知字段？

**AI 建议：必须保留。** 应用写配置时，不应根据当前强类型配置对象重新生成整份 TOML，否则会丢失：用户注释；自定义字段；新版本添加但旧客户端尚不认识的字段；原有分组和排列；用户用于运维说明的文本。建议把 TOML 同时保留为可编辑语法树；PWA 修改某个配置项时，只修改对应节点，其他内容原样保留。无法安全定位或修改时，应拒绝写入并输出错误，而不是重写整份文件。

**用户回答（12:17:19）：** "不，重写即可"

**已确认（12:17:26）：** 应用修改配置时，可以根据当前内存配置**完整重写整个 TOML 文件**；无需保留原注释、字段顺序、格式布局或未知字段。无法识别的字段在重写后可以消失。

# 21. 配置热更新与冲突

> 覆盖对话决策 42（第二问）、43、44（两个子决策）。会话时间：2026-08-01 12:19–12:21。

## 决策 42（第二问）：外部编辑与应用写入冲突时怎么办？

**AI 建议：** 写入前比较当前文件内容哈希：
- Linux S 每次成功加载 TOML 后保存其内容哈希；
- PWA 修改配置时，基于该已加载版本生成新配置；
- 真正写入前重新读取文件；
- 若文件哈希已变化，说明期间有人通过编辑器修改过文件；
- 服务端拒绝本次写入，重新加载外部版本，并通知 PWA 配置已变化；
- 不静默覆盖外部编辑；
- 若哈希一致，则完整生成 TOML，通过临时文件和原子重命名替换。

**用户回答（12:19:35）：** "不检测，强行覆盖，寄希望于监听配置文件的变化，以及写入修改前的物理时间较短，不足以让用户用编辑器修改"

**已确认（12:19:42）TOML 写入冲突策略：**
- 应用写入前不检查文件哈希、mtime 或版本；
- 基于当前内存配置直接完整重写；
- 外部编辑若恰好与应用写入并发，允许被覆盖；
- 依赖文件监听尽快吸收外部变化；
- 不提供冲突合并、恢复或覆盖警告。

## 决策 43：配置监听如何处理文件系统的重复通知？

应用使用"临时文件 + 原子重命名"写 TOML 时，文件监听器可能连续收到创建、重命名、修改等多个通知；编辑器保存也可能产生相同现象。

**AI 建议：** 采用可重置的短暂 debounce，但不忽略应用自己的写入。规则：
- 任意相关文件事件都启动或重置一次约 100 ms 的 debounce；
- debounce 到期后完整读取并校验 TOML；
- 多个连续通知合并为一次加载；
- 应用写完后也通过相同监听路径重新读取文件，验证磁盘内容确实可以成为当前配置；
- 若监听通知丢失，应用写入成功后主动触发一次同样的 reload；
- reload 仍遵循"完整有效才替换，失败则保留最后有效配置"。

这样不存在"内存更新一套、磁盘写入另一套"的双路径语义。

**用户回答（12:20:47）：** "自己要修改配置，也是先落盘后加载，一样的"

**已确认（12:20:53）配置变更只有一条路径：**

```text
生成完整 TOML
→ 写临时文件
→ flush
→ 原子替换正式文件
→ 从正式文件重新读取
→ 完整解析与校验
→ 成功后替换内存配置
```

应用自身修改配置时，也不能直接先改内存；必须先落盘，再通过同一加载逻辑生效。这样磁盘文件始终是唯一权威来源。

## 决策 44（第一问）：何时向客户端确认配置修改成功？

**AI 建议：** 只有新 TOML 已落盘，并从正式文件重新读取、解析和应用成功后，才发送成功事件。若任一步失败：
- 保留最后一次有效内存配置；
- 向 `stderr` 输出完整异常；
- 向发起修改的客户端发送失败事件；
- 不把"文件已写入但尚未成功加载"视为成功；
- 若文件已经被替换成无效内容，则运行时仍继续使用旧配置，等待下一次文件变化。

**用户回答（12:21:07）：** "可以"

**已确认（12:21:12）：** 配置修改只有在 **TOML 已成功落盘，并从正式文件重新读取、完整解析、校验并应用成功后**，才向客户端发送成功事件；否则继续使用上一份有效内存配置，并报告失败。

## 决策 60：四个模式开关由哪里决定？

**AI 建议：** 默认值来自 TOML，命令行只做本次启动覆盖。例如：

```toml
[runtime]
server = true
client = true
pwa = true
fix = false
```

命令行可覆盖：

```text
wanxiang --server=false --client=true --pwa=false --fix
```

优先级固定为：

```text
命令行显式值 > TOML > 程序默认值
```

这样常规部署可以永久配置，临时 doctor、client-only 或修复启动又无需修改配置文件。命令行覆盖仅影响当前进程，不回写 TOML。

```text
命令行显式值 > TOML 配置值 > 程序默认值
```

命令行覆盖只影响本次启动，不回写 TOML。

## 决策 61：程序默认组合是什么？

**AI 建议：** 默认启用 `server + client + pwa`，关闭 `fix`。也就是没有 TOML 对应项、命令行也未显式指定时：

```text

```

- 普通用户直接运行 `wanxiang`，应得到完整 Linux C+S 与 PWA 托管能力；

- headless、client-only、pwa-only 等部署属于显式选择；
- 三个组件虽然同时启用，但桌面客户端仍严格通过 loopback WebSocket 访问本机 S。

# 31. TLS 与监听端点

> 覆盖对话决策 66（两个子决策）、67（两个子决策）。会话时间：2026-08-01 12:43–12:45。

## 决策 66（第一问）：万象 S 是否自己终止 TLS？

**AI 建议：** 首版不内置公网 TLS 证书管理。建议边界：
- loopback 本机连接允许 `ws://127.0.0.1` 或 Unix socket 上的 WebSocket；
- 非 loopback 监听默认只绑定内网地址，是否允许明文由 TOML 显式开启；
- 公网部署由 Caddy、Nginx、Traefik 等反向代理提供 HTTPS/WSS；
- 万象 S 接收代理转发后的 WebSocket；
- 不在首版处理 ACME、证书续期、私钥权限、SNI 与多域名；
- PWA 若通过 HTTPS 加载，只能连接 `wss://`，避免浏览器混合内容限制。

这样能保持单进程业务架构简单，同时不把证书生命周期管理引入首版。

**用户回答（12:43:21）：** "未来用 caddy"

**已确认（12:43:30）：** 首版不内置 TLS 与证书管理；未来公网入口统一交给 **Caddy**，万象只提供其后的 HTTP/WebSocket 服务。

## 决策 66（第二问）：默认监听地址

**AI 建议：** 默认只监听 loopback。

```toml
[network]
listen = "127.0.0.1:8765"
```

这样：本机 Client 可直接连接；Caddy 可反向代理到该地址；未配置 Caddy 时，不会意外向局域网或公网暴露；需要局域网直连时，用户必须显式改为 `0.0.0.0:8765` 或指定网卡地址；`server` 的 WebSocket 与 `pwa` 的静态资源共用该监听器；只有 `pwa-only` 时，该监听器只提供静态资源。

**用户回答（12:43:45）：** "嗯"

**已确认（12:43:50）：** 默认只绑定 `127.0.0.1`；任何非本机监听都必须在 TOML 中显式配置。

## 决策 67（第一问）：`server` 与 `pwa` 是否共用监听端点？

**AI 建议：** 分别配置监听端点，但允许默认合并。例如：

```toml
[network.server]
listen = "127.0.0.1:8765"

[network.pwa]
listen = "127.0.0.1:8765"
```

两者地址完全相同时，由同一个 HTTP listener 同时提供 WebSocket 与 PWA 静态资源；地址不同时，则分别监听。这样能自然覆盖 `server + pwa` 同源部署、`server-only`、`pwa-only`、PWA 对外开放而 S 仅留在 loopback 后由 Caddy 代理等部署方式。

**用户回答（12:44:57）：** "就同一个地址，只不过功能可以开启关闭而已"

**已确认（12:45:02）：** `server` 与 `pwa` **永久共用同一个监听地址和 HTTP listener**，不存在两套网络配置。
- `server=true`：启用业务 WebSocket 路由；
- `pwa=true`：启用 PWA 静态资源路由；
- 两者都启用：同源提供 PWA 与 WebSocket；
- 只启用其中之一：同一 listener 只开放相应功能；
- 两者都关闭：不创建 listener。

## 决策 67（第二问）：业务 WebSocket 使用固定路径

**AI 建议：** 固定为 `/ws`，PWA 使用根路径 `/`：

```text

```

未启用的功能直接返回 `404`，不返回"当前模式已关闭"等额外信息。这样 Caddy、PWA 同源连接和客户端配置都只需要一个基础地址。
