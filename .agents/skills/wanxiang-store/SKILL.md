# 02. 存储模型：NDJSON + CQRS、唯一权威

> 覆盖对话决策 3。会话时间：2026-08-01 11:17。

## 决策 3：会话数据由谁作为唯一权威来源？

**AI 建议：** 以 Linux S 为唯一权威数据源。PWA 可以在浏览器本地缓存会话列表、消息和界面设置，以提升加载速度；但缓存不应被视为完整数据库。所有消息创建、编辑、重新生成、版本选择和删除操作，都由 Linux S 确认并持久化后才算成功。首版建议：Linux S 使用 SQLite 保存完整数据；PWA 使用 IndexedDB 做可丢弃缓存；断网时可以查看已缓存内容；首版不支持离线发送、离线编辑及稍后自动合并。

**用户回答（11:17:39）：** "Linux S 使用 NDJson + CQRS 作为永久存储，内存放事件积分后的状态作为日常使用，严格单进程（多开则互相完全无关），PWA 端缓存先不做，除了要显示的内容外都不存。断网则报错即可。"

**已确认（11:17:51）首版存储与运行模型：**
- **Linux S：NDJSON 事件日志 + CQRS**
- 日常查询读取事件折叠后的**内存状态**
- 单个 S **严格单进程**
- 多开实例之间完全隔离，不共享数据、不协调写入
- PWA 不做持久缓存，只在运行内存中保留当前显示所需内容
- 网络断开立即报错，不提供离线能力或自动重试队列

> 注：这覆盖了原数据模型中的消息版本、版本选择和会话顺序等状态，但永久存储方案明确以 NDJSON 事件模型为准，而不是材料中建议的 SQLite。

# 03. 写入确认与 flush

> 覆盖对话决策 4。会话时间：2026-08-01 11:18。

## 决策 4：何时向客户端确认写操作成功？

**AI 建议：** 采用"先持久化事件，再修改内存状态，再响应成功"的严格顺序：

```
校验命令 → 生成事件 → 追加 NDJSON → flush + fsync → 投影到内存 → 返回成功
```

这样即使进程在任意位置崩溃：
- 响应成功的操作一定已经落盘；
- 已落盘但尚未更新内存的事件，会在重启重放时恢复；
- 不会出现 PWA 收到成功、服务器重启后操作却消失的情况。

代价是每次写入执行 `fsync` 会降低吞吐量，但聊天应用写入频率通常不高，首版更应优先保证语义清晰和数据可靠。

**用户回答（11:18:37）：** "flush 即可，假设我有 UPS"

**已确认（11:18:48）：** 写入成功条件为 **NDJSON 追加并完成用户态 `flush`**，不执行 `fsync`；接受数据仍可能停留在操作系统页缓存中的风险，并以 UPS 作为断电保障。

# 04. 提交原子性

> 覆盖对话决策 5。会话时间：2026-08-01 11:19。

## 决策 5：一个命令产生多个事件时，如何保证原子性？

**AI 建议：** 每个成功命令只追加一条 NDJSON"提交记录"，记录内包含该命令产生的完整事件数组。例如：

```json
{
  "commitId": "01J...",
  "commandId": "01J...",
  "timestamp": "2026-08-01T03:18:00Z",
  "events": [
    { "type": "MessageAdded", "data": {} },
    { "type": "ConversationUpdated", "data": {} }
  ]
}
```

不要把同一命令的多个事件分别写成多行，否则进程可能在两行之间退出，留下只完成一半的业务操作。单行提交记录还能让启动恢复规则保持简单：文件末尾若是不完整 JSON 行，直接截断或忽略该尾行；此前的完整行全部视为已提交。

内存投影应在该整条记录完成 `flush` 后一次性应用；若应用失败，则将进程视为状态损坏并终止，而不是继续提供服务。

**用户回答（11:19:17）：** "可以"

**已确认（11:19:28）：** **一条 NDJSON 记录就是一次原子提交，可包含多个领域事件**。完整行视为已提交；末尾不完整行在恢复时忽略或截断。

> 注：此决策中"投影失败即终止进程"的建议后来被决策 40（故障恢复优先级：截尾 → poison → 崩溃）修正，见本 skill 的 19 节。

# 05. 事件日志组织：全局流、UTC 分文件、全局 id

> 覆盖对话决策 6–7。会话时间：2026-08-01 11:19–11:20。

## 决策 6：事件日志采用全局流还是按会话分流？

**AI 建议：** 采用单一全局有序提交流，物理上允许分段文件。例如：

```text
data/
  events-000001.ndjson
  events-000002.ndjson
  events-000003.ndjson
```

每条提交记录携带全局递增的 `sequence`：

```json
{
  "sequence": 1842,
  "commitId": "01K...",
  "events": [
    {
      "type": "MessageAdded",
      "aggregateType": "Conversation",
      "aggregateId": "conv-123",
      "aggregateVersion": 17,
      "data": {}
    }
  ]
}
```

不建议每个会话或聚合根单独维护文件，原因是：一次命令可能同时影响会话、消息、统计或配置；单一全局顺序可以确定性重放；原子提交不会横跨多个文件；备份、迁移和故障恢复更简单；单进程条件下不需要为多写入者优化。分段只解决文件无限增长问题，不改变它在逻辑上是一条事件流。

**用户回答（11:19:58）：** "按照 UTC 每天分文件"

**已确认（11:20:08）：** 事件日志按 **UTC 自然日**分文件，例如：

```text
events/
  2026-08-01.ndjson
  2026-08-02.ndjson
```

提交记录归属哪个文件，以服务器生成该提交记录时的 UTC 日期为准。跨过 UTC 零点后，下一次提交直接写入新文件；单次提交始终只占一行，因此不会跨文件。整体仍是一条逻辑事件流，只是按日做物理切分。

## 决策 7：跨日期文件是否维持全局序号？

**AI 建议：** 维持实例级、跨文件连续递增的 `sequence`。例如前一天最后一条是 `sequence: 1842`，次日第一条就是 `1843`。启动时按文件名日期排序，逐行重放，并检查序号严格连续。这样可以检测：文件缺失；文件顺序错误；中间记录被删除；重复追加；人工合并或恢复造成的日志断层。日期文件只是存储分区，不应重置事件顺序。

**用户回答（11:20:47）：** "可以，叫做 id 吧"

**已确认（11:20:53）：** 实例级、跨 UTC 日期文件连续递增的全局序号命名为 **`id`**，换日不归零。建议其语义固定为：

```json
{
  "id": 1843,
  "timestamp": "2026-08-01T03:20:00.000Z",
  "events": []
}
```

# 06. 日志恢复：空洞、静默截尾、损坏定义

> 覆盖对话决策 8–10。会话时间：2026-08-01 11:21–11:23。

## 决策 8：`id` 是否允许出现空洞？

**AI 建议：不允许。** 每条成功提交占用一个连续的无符号 64 位整数：
- 第一条提交为 `id = 1`
- 下一条必须为 `id + 1`
- 只有完成整行写入并 `flush` 后，内存中的下一个 `id` 才递增
- 启动重放时，若发现重复、倒序或空洞，立即停止启动并报告日志损坏
- UTC 日期切换只更换文件，不影响 `id`

不要预先分配 `id`，否则命令校验失败或写入失败会制造无意义空洞。单进程模型下，也不需要 UUID、雪花 ID 或时间戳来解决并发分配问题。

**用户回答（11:21:47）：** "同意，而且一旦损坏，自动截尾修复，保留有效前缀，损坏后不读后面的即使是正确行"

**已确认（11:21:55）日志恢复规则：**
- 按 UTC 日期与行顺序读取日志。
- `id` 必须从 1 开始严格连续。
- 遇到首个不完整 JSON、无法解析的提交、错误 `id`、非法事件或投影失败时，立即停止读取。
- 自动将日志截断到最后一条有效提交的末尾。
- 损坏点之后的所有内容一律丢弃，即使后面存在格式正确且 `id` 连续的记录，也不再尝试恢复。
- 截断后，下一个成功提交使用"有效前缀最后一个 `id` + 1"。

这使恢复结果由唯一的最长有效前缀决定，避免扫描后续内容时猜测事务边界或拼接出未经证明的状态。

## 决策 9：截断前是否保留损坏后缀？

**AI 建议：保留。** 自动修复时，先将从损坏字节开始到所有后续日期文件的原始内容移动到独立隔离目录（例如 `corrupt/2026-08-01T032100Z/` 下的 `.tail` 文件），随后再截断正式日志。隔离内容永远不参与自动重放，只用于人工诊断或编写专门恢复工具。

**用户回答（11:22:23）：** "不，静默截尾"

**已确认（11:22:32）：** **发现损坏时静默截尾，不保留损坏后缀，也不生成隔离副本。** 恢复规则因此是：
- 保留首个损坏点之前的最长有效前缀；
- 截断当前损坏文件；
- 删除损坏点之后所有日期文件；
- 不读取、不尝试恢复任何后续记录；
- 从最后有效 `id + 1` 继续写入。

## 决策 10：哪些问题算"日志损坏"？

**AI 建议：** 只把以下情况视为损坏并触发截尾：
- JSON 无法解析；
- `id` 不连续；
- 提交记录缺少必要字段；
- 事件类型未知；
- 事件数据无法反序列化；
- 事件违反结构性不变量，导致无法安全投影。

但**不要**因为普通业务状态不再符合当前版本规则就截尾。例如某旧事件在新版业务规则下已不允许，不应因此销毁后续历史；应通过事件版本迁移或兼容投影处理。

**用户回答（11:22:49）：** "同意"

**已确认（11:23:01）：** **只有无法确定性重放的结构性错误才触发静默截尾**；旧事件与新业务规则不兼容时，必须通过兼容读取或迁移处理，不能当作日志损坏。项目仍以事件日志重建内存状态，并保留所需的消息版本、会话顺序等语义。

# 07. 状态快照

> 覆盖对话决策 11。会话时间：2026-08-01 11:25。

## 决策 11：是否引入状态快照？

**AI 建议：** 首版支持快照，但快照仅是可丢弃的启动加速缓存，不是永久事实来源。建议规则：
- NDJSON 事件日志始终是唯一权威来源。
- 定期把当前内存投影写成一个完整快照。
- 快照记录其已包含的最后提交 `id`。
- 启动时先加载最新有效快照，再从 `id + 1` 开始重放日志。
- 快照缺失、版本不兼容或校验失败时，直接删除或忽略，改为从 `id = 1` 全量重放。
- 快照写入采用临时文件后原子重命名，避免半写文件被误用。
- 日志截尾后，任何覆盖到被截掉 `id` 的快照都必须失效。

**用户回答（11:25:00）：** "无需快照，启动时 replay 全部 ndjson。之后可能会引入每周把前面的旧事件日志用快照取代的功能"

**已确认（11:25:10）首版启动与持久化策略：**
- **不使用快照**；
- 每次启动从 `id = 1` 开始，完整 replay 全部 UTC 日志；
- replay 完成并构建内存状态后才进入正常运行；
- "每周用快照替换旧事件日志"只作为未来的压缩功能，不进入首版设计；
- 未来即使引入压缩，快照将成为被替换历史的权威基线，而不只是缓存，因此需要单独设计迁移与校验协议。

# 08. 事件格式版本管理

## 决策 12：事件如何进行格式版本管理？

**AI 建议：** 每个事件拥有独立的整数 `version`，提交记录本身也拥有 `formatVersion`。

```json
{
  "id": 1843,
  "formatVersion": 1,
  "timestamp": "2026-08-01T03:25:00.000Z",
  "events": [
    {
      "type": "chat.message-added",
      "version": 1,
      "data": {}
    }
  ]
}
```

建议语义：
- `formatVersion` 管理整条提交记录外壳的结构；
- `type` 是稳定且永不改义的事件名称；
- `version` 只管理该事件 `data` 的结构；
- 读取旧事件时，通过纯函数逐级升级，如 `v1 → v2 → v3`，再交给当前投影；
- 已写入的 NDJSON 不做原地批量改写；
- 同一个 `type + version` 一旦发布，其字段含义永久固定；
- 业务含义发生根本变化时，创建新事件类型，而不是复用旧名称。

**用户回答（11:26:05）：** "可以"

**已确认（11:26:19）版本策略：**
- 提交外壳使用 `formatVersion`；
- 每个事件使用独立 `version`；
- 已发布的 `type + version` 语义永久固定；
- 旧事件通过逐级升级函数转换为当前结构；
- 不原地改写历史 NDJSON；
- 根本性语义变化创建新的事件类型。

# 09. 命令幂等：commandId / invocationId

> 覆盖对话决策 13–16。会话时间：2026-08-01 11:26–11:32。

## 决策 13：写命令是否需要幂等标识？

**AI 建议：需要。** 每个修改状态的请求都携带客户端生成的 `commandId`。Linux S 将它写入提交记录，并在内存中维护已执行命令索引：

```json
{
  "id": 1843,
  "commandId": "0198...",
  "formatVersion": 1,
  "timestamp": "2026-08-01T03:26:00.000Z",
  "events": []
}
```

同一 `commandId` 再次到达时：
- 不追加新事件；
- 不再次执行副作用；
- 返回第一次执行的相同业务结果，或至少返回原提交 `id`；
- 重启后通过 replay 恢复幂等索引。

这主要解决：S 已完成 `flush`，但响应在网络中丢失，PWA 不知道操作是否成功而重试。没有幂等键，就可能重复发送消息、重复创建会话或重复批准工具调用。

**用户回答（11:26:43）：** "可以"

**已确认（11:26:54）：** 所有写命令都必须携带唯一 `commandId`，Linux S 会将其写入提交记录，并通过完整 replay 恢复幂等索引。重复命令不会重复追加事件或执行副作用。

## 决策 14：`commandId` 的作用域与生成方式

**AI 建议：** 由客户端生成 UUIDv7，并在该 Linux S 实例的整个历史中全局唯一。具体语义：
- PWA、Linux 本地客户端、其他远程客户端都在发出命令前生成 `commandId`；
- 同一次逻辑操作的网络重试必须复用原 `commandId`；
- 用户主动再次执行相同操作，必须生成新 `commandId`；
- S 永久保留已执行 `commandId → commit id` 的映射；
- 两个不同客户端若意外使用同一个 `commandId`，第二个请求直接视为重复命令；
- UUIDv7 只用于命令幂等，不参与事件排序；事件顺序仍以连续整数 `id` 为准。

不建议由服务器生成，因为客户端在响应丢失后将无法证明重试的是同一命令。

**用户回答（11:27:07）：** "可以"

**已确认（11:27:17）：** `commandId` 由客户端生成，采用 UUIDv7；同一逻辑操作重试必须复用原值，新操作必须生成新值。事件提交顺序仍只由连续整数 `id` 决定。

> 注：`commandId` 的生成方式随后被决策 15 修改——改为 `SHA-256(协议版本 + invocationId + 命令类型 + 规范化载荷)` 的确定性哈希，`UUIDv7` 只用于 `invocationId`，以实现版为准。

## 决策 15（第一问）：相同 `commandId` 但命令内容不同，如何处理？

**AI 建议：将其视为协议冲突并拒绝，绝不能当作普通重复命令。** 每次提交额外记录命令类型与规范化内容摘要：

```json
{
  "id": 1843,
  "commandId": "0198...",
  "commandType": "chat.send-message",
  "commandHash": "sha256:...",
  "events": []
}
```

收到已存在的 `commandId` 时：
- `commandId` 与规范化内容哈希（`canonicalCommandHash`）均相同：视为安全重试，不执行新操作，返回原提交 `id`；
- 任一不同：返回 `409 CommandIdConflict`，不写日志；
- 哈希应基于命令的规范化业务内容，不包含发送时间、认证令牌等传输元数据。

否则客户端 Bug、UUID 被错误复用或恶意请求可能把两个不同操作混成一次幂等操作，产生难以诊断的数据丢失。

**用户回答（11:29:05）：** "commandId 不是随机取的，而是结合了 hash 功能"

**已确认（11:29:10）：** `commandId` 不是随机 UUID，而是**由命令内容确定性计算出的哈希标识**。因此同一逻辑命令只要规范化内容一致，就天然得到相同 `commandId`；内容变化则标识变化。

## 决策 15（第二问）：`commandId` 是否包含客户端身份？

**AI 建议：包含。** 建议计算方式：

```text
commandId =
  base64url(
    SHA-256(
      protocolVersion
      + clientId
      + commandType
      + canonicalPayload
    )
  )
```

其中：
- `canonicalPayload` 使用固定的 JSON 规范化规则，例如对象键排序、UTF-8、数字格式固定、不保留无意义空白；
- 不包含发送时间、访问令牌、网络地址等传输数据；
- `clientId` 是客户端安装或会话的稳定身份；
- `protocolVersion` 防止未来规范化算法变化时发生跨版本碰撞。

加入 `clientId` 很重要：否则两个客户端发送内容完全相同的消息时，会被误判为同一次命令。比如两个用户都发送"你好"，其业务操作应该分别执行，而不是因为内容相同被去重。

**用户回答（11:29:55）：** "同一逻辑命令如果要真的执行两次呢？需要把时间注入或者更优雅的方法"

**AI 修正建议（11:30:06）：** 不要把"当前时间"直接当作去重依据。时间戳会带来精度、时钟回拨和重试重算等问题，而且会把"命令内容"与"执行次数"混在一起。更优雅的做法是拆成两个概念：
- **命令内容**：`commandType + canonicalPayload`
- **本次执行身份**：客户端为每次"确实想执行一次"生成一个 `invocationId`

```text
commandId =
  Base64Url(
    SHA-256(
      "command:v1"
      + invocationId
      + commandType
      + canonicalPayload
    )
  )
```

语义如下：
- 网络重试：复用同一个 `invocationId`，因此得到相同 `commandId`。
- 用户再次执行完全相同的操作：生成新的 `invocationId`，因此得到新的 `commandId`。
- 载荷被错误修改但仍复用 `invocationId`：哈希结果不同，可以检测为客户端协议错误。
- 时间可以存在于 UUIDv7 形式的 `invocationId` 中，方便观察和排序，但不能依赖时间本身保证唯一性。

示例（两次发送相同文本）：
```text
第一次：
invocationId = A
payload = "你好"
commandId = hash(A + SendMessage + "你好")

重试第一次：
invocationId = A
payload = "你好"
commandId 相同，不重复执行

用户再次发送：
invocationId = B
payload = "你好"
commandId 不同，正常执行第二次
```

**AI 建议：** `invocationId` 使用客户端每次操作生成的 UUIDv7；`commandId` 是包含该 `invocationId` 和规范化命令内容的 SHA-256。

## 决策 15（第三问）：把"执行次数"交给独立的 `invocationId` 表达

**问题：** 是否同意把"执行次数"交给独立的 `invocationId` 表达，而不是直接向命令内容注入时间？

**用户回答（11:30:59）：** "可以"

**已确认（11:31:07）幂等模型：**
- `invocationId` 表示"这一次确实想执行"；
- 同一次网络重试复用原 `invocationId`；
- 再执行一次相同逻辑命令时生成新的 `invocationId`；
- `invocationId` 推荐使用 UUIDv7；
- `commandId = SHA-256(协议版本 + invocationId + 命令类型 + 规范化载荷)`；
- 时间只可作为 UUIDv7 的组成特征，不直接参与业务去重。

## 决策 16：Agent 内部触发的命令如何标识？

**AI 建议：** 每个内部命令也生成独立 `invocationId`，同时记录因果关系：

```json
{
  "invocationId": "内部命令自己的 UUIDv7",
  "causationId": "直接导致它发生的 commandId",
  "correlationId": "最初用户命令的 commandId"
}
```

这样：每一步都能独立幂等重试；`causationId` 能还原直接调用链；`correlationId` 能把一次用户操作产生的完整 Agent 流程串起来；不应让所有子操作共用最初的 `invocationId`，否则不同命令会被错误合并。Agent Framework 只是执行层，最终状态变化仍必须通过这些正式命令和事件进入 CQRS 日志。

**用户回答（11:31:58）：** "invocationId 可以，因果链似乎不重要"

**已确认（11:32:04）：**
- Agent 内部命令也使用独立 `invocationId`；
- 首版不记录 `causationId`、`correlationId`；
- 不维护完整因果链；
- 需要排查时，依靠会话、消息、任务等领域 ID 关联即可。

# 19. 提交协调器与故障恢复

> 覆盖对话决策 39、40（三个子决策）。会话时间：2026-08-01 12:05–12:10。
> 本主题修正了决策 5 中"投影失败即终止进程"的早期建议（见本 skill 的 04 节）。

## 决策 39：所有永久写入是否经过单一提交协调器？

**AI 建议：是。** 虽然不同会话的模型调用和 Tool 执行可以并行，但所有会改变永久状态的操作都应进入一个进程内的 FIFO 提交协调器：

```text
并行执行 Provider / Tool
        ↓
生成完整消息或业务事件
        ↓
全局 Commit Coordinator
        ↓
重新校验前置条件
        ↓
分配连续 id
        ↓
追加当日 NDJSON + flush
        ↓
更新内存投影
        ↓
向观察者发布权威增量
```

这样可以天然保证：全局 `id` 严格连续；同一时刻只有一个任务写 NDJSON；文件换日不会发生竞争；内存投影顺序与日志顺序完全一致；多客户端并发命令能在最终提交点再次检查陈旧状态；不需要文件锁、原子计数器或复杂事务。Provider 流式调用、Tool 执行和查询不占用协调器；只有最终完整消息或其他永久事件进入协调器，因此不会把长任务串行化。

**用户回答（12:05:03）：** "可以，但这个就是和 ndjson 单写者是同一者"

**已确认（12:05:10）：** **Commit Coordinator 与 NDJSON 单写者是同一个进程内组件**，不再拆成两层。它独占并负责：
- 分配连续全局 `id`；
- 选择当前 UTC 日期文件并处理换日；
- 序列化整条原子提交；
- 追加并 `flush`；
- 按日志顺序更新内存投影；
- 向观察者发布权威增量。

Provider、Tool 和查询可以并行，但任何永久状态变化都必须交给这个单写者。

## 决策 40（第一问）：落盘成功但内存投影失败时怎么办？

**AI 建议：** 立即终止进程，不回滚日志，也不继续服务。因为提交完成 `flush` 后，NDJSON 已是权威事实。若内存投影无法应用：不发送 `committed`；不尝试从日志删除刚写入的记录；停止接受新命令；退出进程；下次启动从头 replay；若 replay 仍无法确定性应用该提交，则按既定规则把它视为首个损坏点并静默截尾。继续运行会造成日志与内存状态分叉；运行时倒改日志则会破坏追加式模型。

**用户回答（12:07:16）：** "best effort 继续服务，同时向 stderr 打印异常信息。将污染的部分设置为 poisoned，保持现场，不污染的部分照常工作。"

**已确认（12:07:27）运行时策略：**
- NDJSON 已 `flush` 后，内存投影失败时不回滚日志，也不终止进程；
- 将异常完整写入 `stderr`；
- 标记受影响部分为 `poisoned`，保留故障现场；
- 任何依赖该污染部分的查询与写命令都拒绝；
- 不相关的会话、配置和业务投影继续正常工作；
- 单写者继续处理后续可安全应用的提交。

（对话指出：这与此前"启动 replay 遇到投影失败就静默截尾"的规则存在冲突：同一条合法日志可能在运行时被保留，重启时却被截掉。）

## 决策 40（第二问）：启动 replay 时投影异常是否也采用 poisoned？

**AI 建议：是。** 重新定义损坏边界：
- JSON 不完整或无法解析、提交外壳非法、全局 `id` 不连续：属于**物理日志损坏**，静默截尾；
- Agent Framework payload 无法反序列化，或投影代码处理某条合法事件时抛异常：不截尾，记录 `stderr`，将相关部分标为 `poisoned`，继续 replay 其他互不依赖的部分；
- 后续涉及 poisoned 部分的事件保留但不应用，以维持现场；
- 不受影响的投影继续恢复并提供服务。

**用户回答（12:09:23）：** "第一性原理：截尾是代价最小的，poison 次之，崩溃最坏。自行推导这意味什么。"

**AI 推导结论（12:09:33）：** 错误处理按**"截尾 → poison → 崩溃"的固定优先级**执行，不根据"物理损坏还是投影异常"预先选择不同路线。具体意味着：
- 启动 replay 遇到首个无法可靠应用的提交：从该提交开始静默截尾，删除所有后续内容，以最后有效前缀继续启动。
- 运行时刚完成 `flush`，但该提交无法应用到内存投影：因为单写者尚未处理下一条提交，直接截掉刚写入的尾行，保持原内存状态并继续服务。
- 只有在**不能安全截尾**时才 poison，例如日志文件无法修改，但故障能明确隔离到某个会话或投影；此时相关部分停止读写，其他部分继续服务。
- 只有截尾失败且无法隔离、全局顺序或核心内存状态已经无法信任时，才崩溃退出。
- 所有异常都写入 `stderr`，但不额外保留被截掉的数据。

因此，合法 JSON、Agent Framework 反序列化失败、投影代码异常、事件结构不兼容等，在恢复策略上没有本质区别：**能通过丢弃尾部恢复一致性，就先截尾。**

## 决策 40（第三问）：运行时截掉失败提交后是否复用其 `id`？

**AI 建议：复用。** 截尾后该提交从权威历史中不存在，下一次成功提交继续使用相同的连续 `id`，以维持"从 1 开始无空洞"的不变量。

**用户回答（12:10:40）：** "可以。但 stderr 要忠实，否则再无证据"

**已确认（12:10:45）：**
- 运行时截尾后，下一次成功提交复用被删除提交的 `id`；
- `stderr` 是唯一剩余证据，因此必须尽可能忠实记录；
- 不保存损坏后缀、不生成隔离副本、不额外写诊断文件。

建议每次截尾至少输出一条结构化 JSON 到 `stderr`，包含：

```json
{
  "level": "error",
  "event": "ndjson-tail-truncated",
  "utc": "2026-08-01T04:10:00.000Z",
  "phase": "runtime-commit",
  "file": "events/2026-08-01.ndjson",
  "commitId": 1843,
  "byteOffset": 927441,
  "exceptionType": "...",
  "exceptionMessage": "...",
  "stackTrace": "...",
  "rawCommit": "...",
  "action": "truncate-and-reuse-id"
}
```

其中 `rawCommit` 应是即将被截掉的完整原始行；若原始内容可能包含密钥，则仍然忠实输出，因为我们已经选择"stderr 是最后证据"，运维侧必须把 stderr 当作敏感日志保护。

# 45. 自动问答 二：日志格式与恢复（Q111–120）

**111. 问：commit 外层至少包含哪些字段？**
答：`formatVersion`、全局 `id`、`committedAtUtc` 和有序 `events`。事件包含稳定 `type`、`version` 与 payload。

**112. 问：`committedAtUtc` 能否参与一致性判断？**
答：不能。它只用于审计和展示；顺序与身份只由全局 `id` 决定。

**113. 问：一个 commit 内的多个事件是否有顺序？**
答：有，数组顺序就是领域应用顺序，发布后不可改变。

**114. 问：多事件 commit 的投影更新是否原子？**
答：是。要么整条 commit 的全部事件成功应用，要么整条 commit 被截断、隔离或触发崩溃处理。

**115. 问：NDJSON 使用什么文本格式？**
答：UTF-8，无 BOM；每条 commit 序列化为一行，以 `\n` 结束。

**116. 问：事件 payload 是否要求统一字段顺序？**
答：日志本身不依赖字段顺序；只有生成 `commandId` 的规范化 payload 必须使用稳定 canonical JSON。

**117. 问：日志中是否允许非有限浮点数？**
答：不允许 `NaN`、正负无穷等非标准 JSON 值；命令验证阶段直接拒绝。

**118. 问：日志文件权限如何设置？**
答：创建时仅允许当前 Linux 用户读写；附件目录和 TOML 同样采用最小用户权限。

**119. 问：只读 doctor 检查什么？**
答：配置可读性、目录权限、实例锁、日志文件命名、ID 连续性、JSON/事件版本、投影 replay、附件引用与 blob 存在性，但不修改数据。

**120. 问：`doctor --fix` 可以做什么？**
答：只执行确定性修复：截断无效尾部、移除更晚日志内容、重建派生索引或临时文件。不得猜测业务内容、修改历史事件或清理未引用附件。
