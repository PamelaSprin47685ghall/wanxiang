# 10. 模型生成作为长任务、消息记账

> 覆盖对话决策 17（两个子决策）。会话时间：2026-08-01 11:32–11:34。

## 决策 17（第一问）：模型生成是否作为长任务处理？

一次模型调用可能持续很久、流式输出，也可能超时或失败，不能把网络调用包含在 NDJSON 原子提交中。

**AI 建议：拆成多个短提交。**
1. 接收"发送消息"命令，持久化用户消息和生成任务：`UserMessageAdded`、`GenerationStarted`
2. 完成 `flush` 后立即返回任务 ID。
3. 在内存中执行模型调用，并把流式内容推送给客户端；中间 token 默认不写日志。
4. 模型结束后再提交：`AssistantMessageCompleted` 或 `GenerationFailed` 或 `GenerationCancelled`

这样进程中途退出时，重启 replay 会看到一个未完成的 `GenerationStarted`，可以明确将其标记为中断，而不会留下半条助手消息。

**用户回答（11:32:50）：** "流式过程不记账，完成后才记账。但是客户端要流式展示。"

**已确认（11:33:00）生成写入语义：**
- 模型输出的流式 token **不写入 NDJSON**；
- Linux S 通过 SSE 或 WebSocket 将临时增量实时推送给客户端；
- PWA 仅在内存中拼接并展示临时内容；
- 生成完整结束后，才把最终助手消息作为一次原子提交写入事件日志；
- replay 后只会出现完整助手消息，不会出现半截流式内容。

## 决策 17（第二问）：用户消息何时记账？

**AI 建议：** 用户消息先持久化，助手消息完成后再单独持久化。流程为：

```text
用户发送
→ flush 用户消息事件
→ 启动模型生成
→ 向客户端流式推送临时助手内容
→ 生成成功
→ flush 完整助手消息事件
```

若生成期间进程退出、模型失败或用户取消：
- 用户消息仍永久存在；
- 临时助手内容全部消失；
- 日志中没有半成品助手消息；
- 用户之后可以针对该用户消息重新生成。

不建议等模型完成后再把用户消息和助手消息一起记账，因为长时间生成期间，用户刚发送的消息也没有可靠落盘；进程退出后，连用户输入都会丢失。

**用户回答（11:33:56）：** "用户消息，助手消息，tool 消息，tool result 消息，都分别触发记账"

**已确认（11:34:08）：** 以下每一类消息都独立触发一次原子提交并分配新的连续 `id`：
- 用户消息；
- 助手消息；
- Tool 调用消息；
- Tool Result 消息。

流式增量仍然只是临时展示；只有形成完整消息后才提交。因此一次典型流程可能产生四次或更多独立记账：

```text
UserMessage
→ AssistantToolCall
→ ToolResult
→ AssistantMessage
```

每一步完成 `flush` 后，才进入内存状态并向客户端确认。这样可以完整保留 Agent 与工具交互历史。

# 11. 消息模型与 Agent Framework 透明映射

> 覆盖对话决策 18（三个子决策）、19（两个子决策）、20。会话时间：2026-08-01 11:35–11:42。

## 决策 18（第一问）：重启后如何处理"已有 Tool 调用，但没有 Tool Result"？

**AI 建议：** 默认不自动重新执行。原因是工具可能包含发邮件、写文件、调用远端服务等副作用。进程可能在工具实际成功后、Tool Result 提交前退出；自动重跑可能造成重复副作用。建议 replay 后将其识别为"执行结果未知"：保留已经记账的 Tool 调用消息；不伪造 Tool Result；UI 标记为"执行中断／结果未知"；用户显式选择重试时创建新的 `invocationId` 和新的 Tool 调用消息；将来只有明确声明为纯读取或具备外部幂等保障的工具，才可选择自动重试。

**用户回答（11:35:07）：** "只要是完整消息，包括思考消息，也单独记账。已有 Tool 调用，但没有 Tool Result，诸如此类问题，我们先透明化处理，上游 provider 会处理的。"

**已确认（11:35:14）：**
- **任何完整消息都单独记账**，包括：
  - 用户消息
  - 助手文本消息
  - 助手思考／推理消息
  - Tool Call 消息
  - Tool Result 消息
  - Provider 返回的其他完整消息类型
- 流式增量不记账，只在一条消息完整后提交。
- 对"有 Tool Call、无 Tool Result""有思考、无最终回答"等不完整业务序列，应用层**不修复、不补写、不自动重试、不额外标记异常**。
- replay 后忠实呈现已有消息序列，并将其原样继续交给上游 Provider；如何续接或处理由 Provider 决定。

这意味着日志只保证每条已提交消息自身完整，不保证一次 Agent 回合在业务上完整闭合。

## 决策 19（第一问）：Agent Framework 升级后，旧消息如何兼容？

**AI 建议：** 每条消息事件额外记录产生它的 Agent Framework schema 标识（`framework.name` + `schemaVersion`），但不修改原始 `payload`。不要仅记录 NuGet 包版本，因为包版本不一定等于消息 schema 版本。读取路径：原始 payload → 按记录的 schemaVersion 解码 → 必要时通过适配器转换 → 交给当前 Agent Framework。否则未来升级框架后，一旦其 JSON 字段、判别器或内容块结构改变，完整 replay 可能失败，并触发静默截尾，造成大量有效历史被错误删除。

**用户回答（11:37:42）：** "Agent Framework 自己没有现有机制吗？"

**AI 调研结论（11:37:44，含官方源码核对）：** 有，但它解决的是**框架对象的序列化与恢复**，不是一套明确公开的"长期稳定消息 schema 版本协议"。Agent Framework 已提供：
- `agent.SerializeSessionAsync(session)`：把整个 `AgentSession` 序列化为 `JsonElement`
- `agent.DeserializeSessionAsync(json)`：由同一个 Agent 恢复 session
- `ChatHistoryProvider`：作为本地消息历史的读取、追加集成点

官方文档也明确建议持久化完整 session，而不是只保存消息文本或历史 ID。当前 .NET 实现中，`ChatClientAgentSession.Serialize/Deserialize` 直接使用框架的 JSON 配置进行序列化；`AgentJsonUtilities` 又复用了 `Microsoft.Extensions.AI` 的类型解析器，所以 `ChatMessage`、工具调用、工具结果等多态内容由现有框架机制处理。

但没有看到：session JSON 内明确的 `schemaVersion`、官方的旧版本逐级升级器、对序列化 JSON 格式长期稳定的兼容承诺。且官方说明 session 与具体 Agent／Provider 相关，不保证换 Agent 配置或 Provider 后仍然兼容。

**AI 修正建议：** **首版不自行给 Agent Framework 消息增加 schemaVersion，也不自定义消息转换。使用框架现有序列化机制；NDJSON 只透明保存框架产出的 JSON。** 其中：
- 每条完整消息通过自定义 `ChatHistoryProvider` 捕获并追加到 NDJSON；
- 序列化必须使用 Agent Framework／Microsoft.Extensions.AI 的 JSON 配置，不能用裸 `JsonSerializerOptions.Default`；
- session 中非消息状态使用 `SerializeSessionAsync` / `DeserializeSessionAsync`；
- 我们自己的 NDJSON 提交外壳仍保留 `formatVersion`，因为这是我们负责的格式。

## 决策 20：选择消息级序列化

**AI 建议：首版采用消息级序列化，不持久化整个 `AgentSession`。** 永久状态的基本单位是 Agent Framework 给出的每个完整 `ChatMessage`。一次回调若包含多条消息，则保持原顺序，为每条消息分别生成一次 NDJSON 提交：

```text
完整 ChatMessage
→ Agent Framework 的 JSON 序列化
→ 单独 NDJSON 提交
→ flush
→ 更新内存投影
```

Agent Framework 的 `ChatHistoryProvider` 本来就是外部存取消息历史的扩展边界，负责保持消息顺序与元数据；框架会把已经完成的请求和响应消息交给它。当前实现传递的是消息集合，因此 Provider 可以按顺序拆成逐消息提交。

不选择 session 级的原因是：
- `AgentSession` 不只是消息列表，还可能包含 `StateBag`、记忆、服务端会话 ID，以及 Agent 或 Provider 的专有状态；
- session 与具体 Agent/Provider 绑定，官方明确不保证跨 Agent 配置复用；
- 每产生一条消息就追加一次完整 session，会不断重复此前全部历史。对于本地历史，这会使日志体积近似二次增长；
- session 快照会模糊"每条完整消息单独记账"的既定语义，也与未来才考虑的日志压缩快照重叠。

对应的首版约束是：**应用自己通过 `ChatHistoryProvider` 管理完整历史，启动时 replay 消息事件构建内存历史，再创建新的运行时 `AgentSession`。不依赖 Provider 服务端保存的 conversation/session ID。** Agent Framework 同时使用本地 `ChatHistoryProvider` 与服务端历史可能发生冲突，其当前实现也将这两种模式视为替代关系。

因此：
- **NDJSON 权威数据：逐条 Agent Framework `ChatMessage` JSON**
- **内存状态：replay 后的有序消息集合**
- **`AgentSession`：运行时对象，可随进程退出而丢弃**
- **未来周度压缩：可引入 session 或应用状态快照，但不属于首版**

**用户回答（11:41:59）：** "同意首版采用消息级序列化，并限定为应用托管消息历史、不依赖 Provider 服务端 session 状态"

**已确认（11:42:08）：**
- 首版采用**消息级序列化**；
- 应用通过 `ChatHistoryProvider` 托管消息历史；
- NDJSON 保存 Agent Framework 的完整消息 JSON；
- 启动时 replay 全部消息，恢复内存历史；
- `AgentSession` 仅为运行时对象，不作为永久状态；
- 不依赖上游 Provider 的服务端 session/conversation 状态。

# 12. 会话归属与并行生成

## 决策 21：会话归属信息放在哪里？

Agent Framework 的原始消息 JSON 不一定包含本应用稳定的会话标识，但 replay、查询和向 Provider 提供上下文时，必须知道消息属于哪段对话。

**AI 建议：** 在 NDJSON 事件外壳记录应用级 `conversationId`，不修改 Agent Framework 原始 payload：

```json
{
  "id": 1843,
  "formatVersion": 1,
  "conversationId": "019c...",
  "commandId": "...",
  "timestamp": "2026-08-01T03:42:00Z",
  "events": [
    {
      "type": "agent-message-recorded",
      "version": 1,
      "payload": {
        "...": "Agent Framework 原始消息 JSON"
      }
    }
  ]
}
```

建议语义：
- `conversationId` 是应用自己的稳定 UUIDv7；
- 创建会话时生成，终身不变；
- 每条消息提交必须明确归属一个 `conversationId`；
- Agent Framework 的 `payload` 保持原样；
- replay 时按 `conversationId` 建立各自的有序消息集合；
- Provider 或模型的内部会话 ID 不作为本应用主键。

**用户回答（11:42:40）：** "同意"

**已确认（11:42:50）：**
- `conversationId` 是应用级稳定 UUIDv7；
- 写在 NDJSON 事件外壳中；
- 每条消息必须明确归属一个会话；
- Agent Framework 的消息 `payload` 保持原样；
- Provider 内部会话标识不作为应用主键。

## 决策 22（第一问）：同一会话是否允许并行生成？

**AI 建议：** 同一 `conversationId` 严格串行；不同会话可以并行。具体规则：
- 一个会话同一时刻最多存在一个进行中的 Agent/Provider 运行；
- Tool Call、Tool Result、思考消息和最终助手消息都属于该次运行；
- 当前运行未结束时，新的"发送消息"命令不立即启动另一次生成；
- 用户可先取消当前运行，再发送新消息；
- 会话标题修改、归档等不影响上下文的命令可以独立处理；
- 不同 `conversationId` 的生成任务可以同时运行。

原因是允许同一会话并行运行会产生难以定义的问题：两个运行读取相同历史后分别追加结果，完成顺序又可能不同，最终上下文与客户端看到的流式顺序都不确定。

**用户回答（11:44:00）：** "新的“发送消息”命令总在下一次可插入点插入，例如 tool result 返回 llm 的时候，或者 idle 之后。排队。"

**已确认（11:44:09）：** 同一会话不是简单"运行中拒绝新消息"，而是采用**单会话队列 + 协作式插入**：
- 模型流式输出期间，新用户消息进入队列；
- 到达可插入点时，按顺序加入下一次 Provider 请求；
- 可插入点包括：
  - 当前会话处于 idle；
  - Tool Result 已产生、准备再次调用 LLM；
  - 其他控制权已返回应用层、尚未发起下一次 Provider 调用的边界；
- 不在一次正在进行的 Provider 请求内部强行修改上下文；
- Agent Framework 作为执行层，但调用循环需要由应用层掌握这些边界。

# 13. 排队消息

> 覆盖对话决策 22（第二问）、23、24。会话时间：2026-08-01 11:44–11:46。

## 决策 22（第二问）：排队消息何时持久化？

**AI 建议：** 收到时立即持久化，但区分"已排队"和"已插入"。推荐流程：

```text
收到完整用户消息
→ 写入并 flush「用户消息已排队」
→ 返回客户端：accepted / queued
→ 到达下一个可插入点
→ 写入「消息已插入」
→ 将消息加入下一次 Provider 请求
```

这样能同时满足：用户消息一收到就不会因进程退出而丢失；replay 后可以恢复尚未插入的消息队列；不会因为日志中的物理提交顺序，错误地把用户消息塞进 Tool Call 与 Tool Result 之间；Agent Framework 原始消息 JSON 仍保持透明，排队状态放在我们自己的事件外壳中。只在插入时才落盘虽然更简单，但运行期间收到的排队消息会在崩溃后消失。

**用户回答（11:45:06）：** "只在插入时才落盘即可，排队消息可以容忍丢失"

**已确认（11:45:16）：** 排队中的用户消息仅存在于内存，**只有到达可插入点时才写入 NDJSON 并 `flush`**。服务器崩溃或进程退出时，尚未插入的排队消息允许丢失；replay 不恢复队列。

## 决策 23：客户端如何确认排队消息？

**AI 建议：** 区分临时接收与正式记账两种状态：
- 收到请求并放入内存队列后，立即返回 `queued`，但这不代表持久化成功；
- PWA 将消息显示为"等待插入"；
- 到达插入点、消息写入并 `flush` 后，服务器推送 `committed` 及对应日志 `id`；
- 只有 `committed` 才算发送成功；
- 若服务器在此之前断开，PWA 显示发送失败，用户可以重新发送；
- 重试必须复用原 `invocationId`，避免原消息其实已提交但确认包丢失时重复记账。

**用户回答（11:46:31）：** "可以"

**已确认（11:46:40）客户端状态语义：**
- 入队后返回 `queued`，仅表示进入当前进程内存队列；
- 到达插入点后，消息写入 NDJSON 并 `flush`；
- 随后推送 `committed` 和日志 `id`；
- 只有 `committed` 才表示正式发送成功；
- 断线前未提交的排队消息允许丢失。

## 决策 24：一次插入点处理几条排队消息？

**AI 建议：** 到达插入点时，将当时已经排队的所有用户消息按服务器接收顺序一次性排空。处理顺序：

# 36. fork 语义深化

## 决策 78：是否允许多层 fork？

**AI 建议：** 允许任意深度的 fork 链。例如：

```text
A
└─ B（从 A fork）
   └─ C（从 B fork）
      └─ D（从 C fork）
```

规则建议为：
- 新分支只引用它的**直接父对话**；
- 不复制或扁平化祖先消息；
- 创建 fork 时，父对话必须已经存在；
- `forkAfterId` 必须指向父对话当前可见历史中的有效消息提交；
- 父关系创建后不可修改，因此不会形成循环；
- 查询时递归展开祖先前缀，内存中可缓存展开结果；
- 未来压缩功能负责把过深的共享结构重新整理，而不是首版限制 fork 深度。

**用户回答（13:00:58）：** "可以"

**已确认（13:01:07）：** 允许任意深度的不可变 fork 父链；新分支只引用直接父对话，不复制或扁平化祖先历史。

## 决策 79：消息是否需要独立 `messageId`？

**AI 建议：** 不需要。直接使用记录该消息的全局提交 `id` 作为应用级消息标识。理由：
- 每条完整消息本来就单独记账，因此天然拥有唯一且永久的提交 `id`；
- fork 点已经使用该 `id`；
- 删除、引用、回复、编辑 fork、附件归属都可以引用同一个值；
- 避免同时维护 `messageId` 与 `commitId` 两套身份；
- Agent Framework 原始 payload 仍保持透明，其内部可能存在的 ID 不作为万象的权威标识；
- 一个原子提交若包含 fork 元数据和第一条消息，该提交 `id` 就是该消息的标识。

例外是一个提交包含多条消息，但此前已经确定**每条完整消息分别触发记账**；因此普通消息提交始终只含一条消息。

**已确认（13:01:29）：** 每条完整消息直接使用其全局 NDJSON 提交 `id` 作为消息标识，不额外生成 `messageId`。

## 决策 80：fork 后父分支的后续删除是否影响子分支？

**AI 建议：** 不影响。子分支继承的是 fork 创建时的历史快照，而不是父分支的实时投影。否则会出现这种问题：

```text
A 中有消息 10、11、12
B 从 A 的消息 12 之前 fork
之后 A 删除消息 11
```

若 B 每次都读取 A 的当前状态，B 的历史也会被间接改变，这违背"分支创建后不可变"的语义。因此 fork 元数据除了 `parentConversationId`、`forkAfterId`，还应隐含或显式保存一个时间边界：`forkBaseCommitId = 创建该 fork 的提交 id`。解析子分支历史时，只考虑父分支在 `forkBaseCommitId` 时已经发生的事件；父分支之后的新增、删除或其他 tombstone 都不影响子分支。

**用户回答（13:01:41）：** "可以"

**已确认（13:01:48）：** fork 继承的是**创建时快照**。因此子分支展开父历史时：
- 只考虑 `forkBaseCommitId` 及之前已经成立的父分支状态；
- 父分支之后新增、删除、再次 fork 或其他变化，都不影响既有子分支；
- 子分支一旦创建，其继承前缀即固定不变。

## 决策 91：一次 Tool 循环是否沿用同一个 `generationId`？

## 决策 92：一次响应包含多个 Tool Call 时，是否并行执行？

- 各 Tool 独立并行执行；

**151. 问：Provider 定义来自哪里？**

答：只在该配置本身被声明为必需却无效时拒绝整份 TOML；某会话引用了后来不可用的 Provider，则生成时失败，不篡改会话配置。

答：不保存。部分 delta 消失，只记录运行失败状态；没有完整消息就没有永久消息事实。
