# 41. 反推出的第一性原理（12 条）

> 以下是根据前 100 个回答归纳出的设计哲学，并非原始文件的逐字内容。会话时间：2026-08-01 13:32。

## 1. 确定性优先于灵活性

系统应尽量只有一种明确解释：
- 一个永久写入入口；
- 一个全局连续提交序号；
- 一个配置事实来源；
- 一个真实网络通信路径；
- 完整快照优于补丁；
- 精确版本相等优于复杂兼容协商；
- 明确失败优于隐式猜测和自动修复。

当两个方案功能相近时，默认选择状态空间更小、replay 更容易、失败语义更明确的方案。

## 2. 只持久化已经成为事实的东西

永久事实必须满足：
1. 已形成完整业务对象；
2. 已经通过单写者；
3. 已追加并 `flush`；
4. 能从日志确定性重放。

因此：
- 完整消息持久化；
- 流式 delta 不持久化；
- 排队消息不持久化；
- observe、cursor、generation、取消状态不持久化；
- 正在运行的 Provider、Tool 和上传过程属于运行时；
- "已发送到客户端"不等于"客户端已应用"；
- "进入队列"不等于"发送成功"。

## 3. 追加历史，不改写过去

历史一旦发布便保持语义稳定：
- NDJSON 只追加；
- 删除使用 tombstone；
- 编辑通过 fork；
- 旧事件通过升级函数读取；
- 不重写历史；
- 父会话后续变化不影响已有分支；
- 附件先保留，未来压缩时再做可达性回收。

任何需要"修改旧事实"的需求，默认建模为新的事实。

## 4. 永久状态串行，外部工作并行

必须严格串行的只有永久提交临界区：

```text
分配 id
→ 序列化
→ append
→ flush
→ 更新投影
→ 发布权威变化
```

Provider、Tool、MCP、网络读取和附件传输可以并行。并行结果可以按完成顺序记账，但再次交给 Provider 时恢复原 Tool Call 顺序。

也就是：**并发计算，串行承诺。**

## 5. 不自动重复可能产生副作用的操作

只要执行结果存在歧义，就不能假设它没有发生：
- MCP 崩溃中的调用不自动重放；
- Tool 超时或断连不自动重试；
- Provider 失败不进行隐藏重试；
- 配置更新不重启在途调用；
- 取消无法真正停止 Tool 时，迟到的完整结果仍忠实记账。

重试必须是新的显式决策；只有明确属于同一次逻辑执行时才复用原 `invocationId`。

## 6. 权威状态不能被慢客户端拖住

客户端是观察者和命令发起者，不是服务端进度的一部分：
- 每条连接拥有独立 cursor；
- 慢客户端从自己的位置追赶；
- 追赶期间暂停不可重放的实时流；
- 慢客户端不阻塞 Agent、写入器或其他客户端；
- 写命令只检查它实际涉及的投影是否追平；
- 无关提交可以跨越。

默认采用局部相关性，而不是全局同步屏障。

## 7. 传输层保持薄，业务标识承担关联

WebSocket 只运输独立事件，不建设第二套 RPC 系统：
- 无通用 request/response；
- 无传输层 requestId；
- 无通用 streamId；
- 使用 `conversationId`、`invocationId`、`commandId`、`generationId` 等业务标识；
- 断线后重新观察权威状态，而不是重放所有网络帧。

只有确实属于运行时业务实体的标识才存在，例如临时 `generationId`。

## 8. 故障恢复以最长可信前缀为边界

系统不尝试猜测损坏内容的意图：
- 保留最长有效前缀；
- 从首个不可恢复点截断；
- 后续内容即使看似有效也不采用；
- 尾部提交失败时尽量截断并复用 ID；
- 无法截断时才考虑隔离；
- 既不能截断也不能隔离才崩溃。

恢复目标不是最大化抢救数据，而是恢复一个**确定、连续、可解释**的历史。

## 9. 配置必须经过磁盘才能成为现实

配置不是内存中的可变对象，而是磁盘 TOML 的投影：

```text
生成完整 TOML
→ 同目录临时文件
→ flush
→ 原子 rename
→ 重新读取正式文件
→ 完整解析和验证
→ 替换内存配置
```

因此：
- 外部编辑和应用内编辑走同一路径；
- 无局部应用；
- 无内存先改；
- 无普通 watcher 自动修复；
- 新配置影响新工作；
- 旧工作按旧配置排空。

## 10. 上游数据透明，应用元数据外置

Agent Framework 的完整消息 JSON 应原样保存。万象只在外层增加自身所需的：
- `conversationId`
- commit `id`
- 事件类型和版本
- 分支关系
- 配置快照
- 其他应用级元数据

不重新发明 Agent 消息模型，也不把展示层结构误当成永久领域模型。

## 11. 首版优先边界清晰，而不是能力完备

首版明确推迟：
- TLS 内建；
- RBAC 和审批；
- Snapshot；
- 压缩与附件 GC；
- Token 原地轮换；
- 通用帧重放；
- 上传续传；
- Provider 会话状态依赖；
- 多进程协调；
- 分布式一致性；
- 沙箱与复杂隔离。

默认规则是：非核心能力只有在缺失会破坏数据正确性时才进入首版。

## 12. 安全模型务实且明确

首版不是零信任平台，但边界不能含糊：
- 默认只监听 loopback；
- 非 loopback 必须显式配置；
- 永久 token 每客户端独立；
- 服务端只存 SHA-256；
- 本地同进程桌面端可自动配对；
- PWA 必须走配对；
- Tool 继承 Linux 用户权限；
- MCP 子进程提供进程边界；
- 不把密钥写入 NDJSON；
- 已知密钥不得出现在 stderr。

不声称拥有尚未实现的权限隔离能力。

# 42. 我将自动采用的后续判断规则（16 条）

> 对话原文（2026-08-01 13:32）。接下来未明确讨论的设计项，默认按这些规则落定：

- 独立工作可并行；永久写入必须经过单写者。
- 热更新只影响新工作；在途工作按旧配置排空。
- 队列默认内存 FIFO，不为运行时队列设计持久化恢复。
- 取消首先是合作式取消，不承诺终止不合作的外部代码。
- 不隐藏重试 Provider、Tool 或 MCP 调用。
- 运行失败通过 WebSocket 临时状态和 `stderr` 报告；除非形成完整 Agent 消息，否则不制造永久"错误消息"。
- 重复或冲突的稳定标识在配置加载时直接判为无效，不采用"最后一个覆盖"。
- Tool 和 MCP 使用稳定、带命名空间的标识，显示名称不作为身份。
- 配置降低并发上限时不终止已运行任务，只限制后续启动。
- 配置提高并发上限时立即从 FIFO 队列补充启动。
- 服务关闭时停止接收新工作，合作式取消运行时任务，排空单写者并 flush；未提交队列允许丢失。
- 后台任务异常不得成为无人观察的异常；写入 stderr，并转换为对应运行失败状态。
- 不增加独立数据库、缓存数据库、消息总线或内部 RPC 层。
- Doctor 只验证和修复可由既定规则确定的问题，不发明业务内容，不做附件 GC。
- 测试重点优先放在 replay、截断恢复、幂等、fork、cursor、配置原子切换和竞争条件，而不是 UI 快照数量。
- 任何优化都不能引入第二个事实来源。

# 43. 只有这些情况我还会提问（5 条）

> 对话原文（2026-08-01 13:32）。只会在下列情况停下来询问：

1. 两个选择都符合上述原则，但决定了明显不同的产品体验；
2. 涉及用户数据保留、隐私或不可逆删除策略；
3. 需要确定具体外部兼容标准，而现有回答不能推出；
4. 需要人为选择数值，例如默认大小上限、时间窗口或资源配额，且没有自然安全值；
5. 新需求与已经确认的原则直接冲突。

除此之外，直接给出自动决策及推导依据，不再累计"第 101、102 个问题"。这套原则延续了原始项目对 F#、Avalonia、Agent Framework、客户端/服务端结构以及 clean-room 实现边界的要求。
