# 本机打开 PWA 能否免配对：威胁模型与结论（r11 · 决策 280–284）

## 问题
用户在**主机所在的电脑**上用浏览器打开 `http://127.0.0.1:8765/`（PWA），目前仍要输入桌面端显示的 6 位配对码。提议：既然是“本机”，是否可以跳过配对？

## 结论
**不实现“按来源地址判定本机即免配对”。** 回环地址只证明“这台机器上的某个进程”，不证明“是用户本人在用万象 PWA”。任何以“来自 127.0.0.1”为凭据的设计都会被下文 T1–T5 中至少一条击穿。

唯一可接受的免码路径是**由桌面客户端发起的一次性令牌**（见“可行设计”），它本质上就是“配对码由程序代填”。本轮没有实现它，只做了它的前置防线（T1/T2 的 Origin + Host 检查），原因见“为何本轮不做”。配对体验本身的改进在 r9/r10 已完成（配对优先、单一主按钮），本轮在截图里复核了输入后的状态。

## 威胁
| # | 威胁 | 若“回环即免配对”会怎样 | 现状 / 本轮处理 |
|---|---|---|---|
| T1 | **跨站 WebSocket 劫持（CSRF/Origin）**：用户访问任意网页，页面 JS `new WebSocket("ws://127.0.0.1:8765/ws")`。浏览器不对 WebSocket 做同源限制，连接来源就是回环。 | 任意网页直接拿到完整会话权限：读全部对话、调用工具（含本机执行）。**致命。** | 此前握手**不检查 Origin**（只靠配对码/令牌挡住）。本轮加入：带 Origin 的握手必须与 Host 同源，否则 403（决策 281）。 |
| T2 | **DNS 重绑定**：`rebind.evil.example` 先解析到攻击者服务器，再改解析到 127.0.0.1。此时 Origin 与 Host 都是 `rebind.evil.example:8765`，同源检查放行。 | 同 T1。 | 本轮加入 Host 白名单：浏览器握手的 Host 只能是 IP 字面量、`localhost`，或 `WANXIANG_ALLOWED_HOSTS` 中登记的域名（决策 282）。 |
| T3 | **同机其他用户 / 其他进程**：多用户 Linux、共享开发机、容器宿主、被入侵的低权限服务，都能连回环端口。 | 任何本地账户都能冒充本人。 | 保持：回环不是凭据；配对码只显示在桌面端窗口里，令牌存在用户自己的配置目录（文件权限保护）。 |
| T4 | **浏览器扩展**：扩展能注入页面、以 PWA 的源发请求，或读取 PWA 存储。 | 扩展无需任何交互即可配对。 | 无法在服务端区分；一次性令牌方案也只能缩短窗口，不能消除。如实写在已知风险里。 |
| T5 | **反向代理 / X-Forwarded-For**：本机 nginx/Caddy/Tailscale Serve/cloudflared 把**远端**请求转发到 127.0.0.1。 | 互联网上的任何人都“来自回环”，直接免配对。**致命。** | 主机不信任 X-Forwarded-For（也不应信任：客户端可伪造）。`isDesktopClient` 除回环外还要求保留名令牌，代理后面的远端拿不到。 |
| T6 | **0.0.0.0 / 局域网监听**：`listen = "0.0.0.0:8765"` 时，局域网设备连到的是同一端口；IPv4 映射的 IPv6 地址（`::ffff:127.0.0.1`）等写法容易误判。 | 判错一次就是局域网免配对。 | 判定统一走 `IPAddress.IsLoopback`（含映射地址）；但即便判对，T1–T5 依然成立。 |

## 可行设计（未来可做，默认关闭）
1. 只有桌面客户端（保留名令牌 + 回环连接，即 `isDesktopClient`）能请求一次性“打开 PWA”令牌：32 字节随机、60 秒过期、单次使用、只存哈希。
2. 桌面端用系统浏览器打开 `http://127.0.0.1:<port>/#pair=<token>`：令牌放在 **fragment**，不进服务端日志、Referer、代理。
3. PWA 读取后立即 `history.replaceState` 清掉 fragment，用令牌走现有的配对流程换长期设备令牌。
4. 握手必须满足决策 281/282（同源 + Host 白名单）。
5. 设备列表里该设备标注“本机浏览器”，可随时吊销。

这样“免码”的凭据是桌面端交出的秘密，而不是网络位置；T1/T2/T3/T5 都拿不到令牌。T4（扩展）残留风险与现在手输配对码相当。

## 为何本轮不做
- 节省的只是一次 6 位数输入，而且只发生在“主机所在电脑上用浏览器”这一少见场景（桌面端本身已自动配对）。
- 需要新协议事件、桌面端“在浏览器中打开”入口、PWA 启动解析，三端改动；先把 T1/T2 堵上，因为它们**今天就影响所有用户**，与免配对无关。
- 已登记为待办（决策 284）。

## 本轮改动
- `Auth.isAllowedWsOrigin`：无 Origin（原生客户端）放行；有 Origin 必须 http(s) 且 host:port 与 Host 头一致；`null`、扩展源、其他端口拒绝。
- `Auth.isAllowedWsHost`：浏览器握手（带 Origin）时 Host 只能是 IP 字面量、`localhost`，或 `WANXIANG_ALLOWED_HOSTS`（逗号分隔）中的域名。
- `/ws` 握手不满足即 403，不升级 WebSocket。
- 测试：`WsOriginTests`（纯函数表 + 真实主机握手）。

## 对部署的影响
通过**域名**反向代理访问 PWA 的用户，需要设置环境变量 `WANXIANG_ALLOWED_HOSTS=wx.example.com`，并让代理原样转发 Host（nginx：`proxy_set_header Host $host;`）。直接用 IP 或 localhost 访问不受影响；桌面端与脚本（不带 Origin）不受影响。
